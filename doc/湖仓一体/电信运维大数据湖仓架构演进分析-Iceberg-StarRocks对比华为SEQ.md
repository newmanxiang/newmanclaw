## 一、问题陈述与核心结论

### 1.1 问题背景

电信运维大数据的两类核心数据：

- **XDR 详单**：会话级明细记录（S1-U/Gn/信令/话单等），单表数十亿~万亿行，日增 TB 级，典型查询是**按 IMSI/MSISDN/会话 ID 等高基数键的点查/明细回溯**。
- **XDR 统计数据**：由详单加工的多粒度汇聚指标（时间 × 区域 × 小区 × 网元 × KPI），数据量同样巨大，查询方式**多样、多维、并发要求高**（运维监控、KPI 报表、即席下钻）。

**我司现状**（架构定型于 2020 年前 Hadoop 生态早期）：

- 详单：**HBase 存索引 + 自研 HDFS 文件存储格式**，查询用**自研查询组件**（针对详单点查定制，**不支持多维查询**）。
- 统计：为满足多维 + 高并发，只能建设**规模巨大的 MPP 数据库集群**。

**两个突出副作用**：

1. **湖仓资源隔离、难以复用**：详单在 Hadoop 湖、统计在 MPP 仓，两套存储 + 两套算力，资源无法弹性互通。
2. **计算被 MPP 绑死**：统计数据之上的加工计算只能写在 **MPP 数据库的存储过程**里，逻辑与引擎强耦合、难维护、难迁移。

**华为对标产品 SEQ**：采用 **CarbonData + Spark + HetuEngine** 作为湖，**GaussDB 作为实时数据库补充**，核心的**存储、计算、查询均在湖内完成**——这正是"湖内存算一体"的形态。

**我司目标**：切换到 **Iceberg + StarRocks**，让**存储与计算的重心回到湖中**。

### 1.2 核心结论（先给答案）

| 问题 | 结论 |
|------|------|
| **技术可行性** | **整体可行，但需分场景**：统计数据场景**高度可行且收益最大**（StarRocks 多维 + 高并发是主场）；XDR 详单**高基数点查**是**最大技术风险点**——Iceberg 无原生二级索引，需用"排序/分桶 + Bloom Filter + Data Cache + 物化视图"组合或"热数据 StarRocks 内表 + 冷数据 Iceberg"分层来补齐。 |
| **vs 华为 SEQ 优势** | 开放格式不锁定、StarRocks C++ 全向量化在多维/高并发交互式查询上更强、用**物化视图替代存储过程**、湖仓统一后**资源可弹性复用**、生态与演进速度更快。 |
| **vs 华为 SEQ 劣势** | SEQ 的 CarbonData 自带**二级索引 + 时空索引 + 内建预聚合**，详单点查与时空查询"开箱即用"；目标架构需自行工程化补齐索引与预计算，且 GaussDB 作为实时仓的成熟度需用 StarRocks 主键表/实时写入对标。 |
| **演进策略** | **先迁统计、后迁详单、最后统一下线**：第一阶段把统计数据迁到 StarRocks（最易见效，直接解决"资源隔离 + 存储过程"两大痛点）；第二阶段 XDR 详单入 Iceberg 并攻克点查；第三阶段统一湖仓、下线自研格式与独立 MPP 集群。 |

**一句话**：方向正确——把存算重心搬回湖中、用开放栈替代自研与 MPP 是对的；**关键不是"能不能搬"，而是"详单高基数点查在 Iceberg+StarRocks 上如何不退化"**，这是整个迁移成败的技术分水岭。

## 二、三种架构画像

### 2.1 华为 SEQ：CarbonData + Spark + HetuEngine + GaussDB

```
            ┌──────────────────────────────────────┐
            │        分析 / 运维 / KPI 应用          │
            └───────────────┬──────────────────────┘
        ┌───────────────────┼───────────────────────┐
        │                                            │
┌───────▼────────┐                         ┌─────────▼─────────┐
│  HetuEngine    │   查询/联邦/下推         │   GaussDB(实时仓)  │
│ (交互式查询)   │                         │  实时数据库补充    │
└───────┬────────┘                         └─────────┬─────────┘
        │                                            │
┌───────▼────────┐   批处理/入湖/加工        ┌────────▼─────────┐
│     Spark      │◄────────────────────────►│  实时写入/点查    │
└───────┬────────┘                          └──────────────────┘
        │
┌───────▼────────────────────────────────────────────────────┐
│           CarbonData（湖内存储格式，自带索引）               │
│  多级索引 + 全局字典 + Sort/二级/时空索引 + 预聚合 DataMap   │
└───────┬─────────────────────────────────────────────────────┘
        │
┌───────▼────────────────────────────────────────────────────┐
│                HDFS / OBS（对象/分布式存储）                 │
└─────────────────────────────────────────────────────────────┘
```

- **存算重心在湖内**：CarbonData 把索引/预聚合内建进格式，Spark 负责批量加工与入湖，HetuEngine 负责交互式与联邦查询；存储、计算、查询都在湖里闭环。
- **GaussDB 仅作实时补充**：承接实时点查/低延迟场景，不是核心存储中心。
- **本质**：**私有重型存储格式 + 湖内闭环**。详单点查靠 CarbonData 二级索引，多维/时空靠多级索引与时空索引，KPI 汇聚靠内建预聚合——加速能力都"沉在格式里"。

### 2.2 我司现状：HBase 索引 + 自研 HDFS 格式 + 自研查询 + 大规模 MPP

```
   ┌─────────────────────┐         ┌──────────────────────────┐
   │   详单查询应用       │         │   统计/多维/报表应用      │
   │  (按用户/会话点查)   │         │  (多维 + 高并发)          │
   └─────────┬───────────┘         └─────────────┬────────────┘
             │                                    │
   ┌─────────▼───────────┐         ┌─────────────▼────────────┐
   │   自研查询组件       │         │     大规模 MPP 集群       │
   │ (详单定制,不支持多维)│         │  存储+计算+存储过程加工   │
   └─────────┬───────────┘         └─────────────┬────────────┘
             │                                    │ (独立存储,独立算力)
   ┌─────────▼───────────────────────────┐       │
   │  HBase 索引  +  自研 HDFS 文件格式   │       │
   └─────────┬───────────────────────────┘       │
             │                                    │
   ┌─────────▼────────────────────────────────────▼──────────┐
   │            两套独立体系，资源隔离、难以复用              │
   └──────────────────────────────────────────────────────────┘
```

- **详单侧**：HBase 维护点查索引（rowkey/二级映射），明细落在自研 HDFS 列式/行式文件；自研查询组件专为"按 key 取明细"定制——**点查高效，但不支持多维分析**。
- **统计侧**：为满足多维 + 高并发，独立建设大规模 MPP；统计加工逻辑写在 MPP **存储过程**中。
- **副作用根因**：详单（湖）与统计（仓）是**两套存储 + 两套算力**，无法弹性复用；加工计算与 MPP 引擎强绑定。

### 2.3 目标架构：Iceberg + StarRocks（湖内存算）

```
            ┌──────────────────────────────────────────────┐
            │     详单点查 + 多维统计 + 报表 + 即席下钻      │
            └───────────────────────┬──────────────────────┘
                                    │ 标准 SQL
            ┌───────────────────────▼──────────────────────┐
            │              StarRocks（C++ 向量化 MPP）       │
            │  FE: CBO/物化视图重写  BE/CN: 向量化执行        │
            │  Data Cache(内存+NVMe) + 异步物化视图 + 资源组 │
            │  内表(主键表/索引) ←热数据   外表↔Iceberg(冷)  │
            └───────────────────────┬──────────────────────┘
                                    │ External Catalog(外表,零搬运)
            ┌───────────────────────▼──────────────────────┐
            │            Iceberg（开放表格式 / 统一表层）     │
            │  metadata/manifest 裁剪 + 隐藏分区 + 排序聚簇   │
            │  数据文件: Parquet/ORC (+Bloom Filter/Puffin)  │
            └───────────────────────┬──────────────────────┘
                                    │
            ┌───────────────────────▼──────────────────────┐
            │            HDFS / S3 / OSS（统一对象存储）      │
            └────────────────────────────────────────────────┘
```

- **存算重心回湖**：一份 Iceberg 数据，StarRocks 既能外表直查（冷/全量），也能把热数据/高频汇聚做成内表或物化视图加速；详单与统计共享同一存储与算力池。
- **加速重心在引擎**：StarRocks 用 Data Cache、物化视图、向量化承担加速；Iceberg 提供精准元数据做文件裁剪。
- **本质**：**开放轻量表格式 + 强向量化引擎 + 统一湖仓**，与 SEQ 的"湖内闭环"理念一致，但用开放栈替代私有格式。

## 三、现状架构的根因剖析与副作用

### 3.1 为什么会形成现状（历史合理性）

| 现状选择 | 当年（2020 前）原因 | 当时的合理性 |
|---------|-------------------|------------|
| HBase 存索引 | 早期 Hadoop 缺少成熟列存表格式（Iceberg 2017 起步、当时未成熟），HBase 是最现实的高基数点查方案 | 合理 |
| 自研 HDFS 文件格式 | Parquet/ORC 当时对电信明细的压缩/裁剪不够理想，CarbonData 属华为私有 | 合理（但埋下锁定隐患） |
| 自研查询组件（仅点查） | 业务首要诉求是详单回溯，多维分析需求尚未爆发 | 合理（但欠缺扩展性） |
| 独立大规模 MPP | 当时湖上引擎（Hive/早期 Presto）无法满足统计的多维 + 高并发 + 低延迟 | 合理（但造成湖仓割裂） |

**关键判断**：现状不是"设计失误"，而是**时代局限下的合理选择**。但随着开放表格式（Iceberg）与向量化湖上引擎（StarRocks）成熟，这些选择的**技术债已显性化**。

### 3.2 现状的核心副作用（迁移要解决的目标）

| 副作用 | 表现 | 业务/工程代价 |
|--------|------|--------------|
| **湖仓割裂、资源不可复用** | 详单（HDFS+HBase）与统计（MPP）两套存储 + 两套算力 | 资源利用率低、扩容各自为政、成本高 |
| **计算与 MPP 强耦合** | 统计加工只能写 MPP 存储过程 | 逻辑黑盒、难测试、难迁移、人才依赖 |
| **详单不支持多维** | 自研查询组件仅按 key 取明细 | 多维分析需把数据再倒进 MPP，链路冗长、时效差 |
| **自研格式/组件维护成本** | 私有格式与查询组件需自行长期维护 | 团队负担重、生态隔离、招聘困难 |
| **数据多副本** | 同源数据在 HDFS、HBase、MPP 多处存储 | 存储浪费、一致性风险 |

## 四、目标架构（Iceberg + StarRocks）技术可行性分析

### 4.1 总体可行性判断

| 子场景 | 可行性 | 关键依据 | 主要风险 |
|--------|-------|---------|---------|
| **统计数据多维 + 高并发** | **高** | StarRocks C++ 全向量化 + 物化视图 + Data Cache，正是其主场 | 低（成熟方案） |
| **详单高基数点查** | **中** | Iceberg 无原生二级索引，需工程化补齐裁剪能力 | **高（核心风险）** |
| **统计加工计算去 MPP 存储过程** | **高** | 用 StarRocks SQL + 异步物化视图替代存储过程 | 中（逻辑迁移工作量） |
| **湖仓统一/资源复用** | **高** | 单一 Iceberg 存储 + StarRocks 统一算力 + 资源组隔离 | 低 |
| **实时写入/实时查询** | **中—高** | StarRocks 主键表 + 实时导入对标 GaussDB | 中（高吞吐实时写入调优） |

### 4.2 统计数据场景：可行性高

统计数据的诉求（多维过滤聚合 + 高并发 + 低延迟）几乎是 StarRocks 的"定义场景"：

- **多维查询**：C++ 全向量化 + SIMD + CBO（基于 Iceberg manifest 统计与 Puffin NDV），多维过滤聚合性能强。
- **高并发**：StarRocks 内表分桶 + 前缀索引 + Bitmap/Bloom Filter 索引，支撑高并发短查询；资源组（Resource Group）做负载隔离。
- **替代存储过程**：把 MPP 存储过程里的汇聚逻辑改写为 **StarRocks 异步物化视图**（透明查询重写 + 分区级增量刷新，Append-only 数据增量刷新尤其友好），加工逻辑从"黑盒过程"变为"声明式 SQL + MV"，可版本化、可测试。
- **湖内存算**：统计明细以 Iceberg 承载，高频汇聚用物化视图/内表加速，**存储与计算回到湖内统一栈**。

> 结论：统计场景迁移**风险低、收益大**，应作为第一优先级，可优先解除"资源隔离 + 存储过程绑定"两大副作用。

### 4.3 XDR 详单场景：可行性中，点查是最大技术风险

这是整个迁移的技术分水岭。详单的核心查询是**数十亿行中按高基数键（IMSI/MSISDN/会话 ID）点查明细**，而：

- **现状**：HBase 索引天然适合高基数点查（按 rowkey/二级索引毫秒级定位）。
- **SEQ**：CarbonData 自带**二级索引**，点查"开箱即用"。
- **Iceberg + StarRocks 外表**：**Iceberg 无原生二级索引**；文件级 min/max 统计对**高基数随机值几乎无裁剪效果**（min/max 区间覆盖全域），即使叠加 Parquet/ORC **Bloom Filter** 也只能做**文件级**过滤，粒度粗于 HBase/CarbonData，存在**点查退化为大范围扫描**的风险。

**可行的补齐方案（按推荐度排序）**：

| 方案 | 机制 | 适用 | 代价/限制 |
|------|------|------|----------|
| **A. 热冷分层（推荐主线）** | 近期热详单放 **StarRocks 内表**（主键表/带 Bloom/Bitmap/前缀索引/可选倒排索引），历史冷详单沉 **Iceberg 外表**；查询按时间路由 | 大多数点查命中近期数据 | 热数据占用 StarRocks 本地/分离存储；冷数据点查仍弱 |
| **B. 排序/分桶聚簇 + Bloom Filter** | Iceberg 写入时按点查键**排序聚簇** + 对点查列建 **Bloom Filter**，配合 StarRocks Data Cache | 点查键与排序键相关性高时 | 高基数随机键聚簇效果有限；写入需排序成本 |
| **C. 外置索引/键值加速层** | 保留/新建轻量 KV 索引（如继续用 HBase 或换 KV 存储）做"键→文件/分区"定位，再由 StarRocks 读 Iceberg | 必须支持冷数据随机点查 | 引入额外组件，部分回到"索引+存储"分离 |
| **D. 跟踪 Iceberg 二级索引/删除向量演进** | Iceberg 社区正推进文件级索引能力 | 中长期 | 2026 初尚未 GA，不能作为当期依赖 |

> 现实建议：**A（热冷分层）为主 + B（排序+Bloom）为辅**，对极端冷数据随机点查保留 **C** 作为兜底。切忌假设"详单全量进 Iceberg 外表即可满足点查"——这是最大可行性陷阱。

### 4.4 组件级迁移映射与可行性

| 现状组件 | 目标组件 | 迁移可行性 | 说明 |
|---------|---------|-----------|------|
| 自研 HDFS 文件格式 | **Iceberg + Parquet/ORC** | 高 | 标准化、跨引擎，去自研维护负担；需数据格式转换/回灌 |
| HBase 详单索引 | **StarRocks 内表索引（热）+ Iceberg 排序/Bloom（冷）/(可选)外置 KV** | 中 | 高基数点查需重点设计（见 4.3） |
| 自研查询组件（仅点查） | **StarRocks SQL** | 高 | 统一 SQL 入口，且天然支持多维查询（补齐现状短板） |
| 统计 MPP 集群（存储+计算） | **Iceberg 存储 + StarRocks 计算** | 高 | 多维/高并发由 StarRocks 承担 |
| MPP 存储过程 | **StarRocks 异步物化视图 + SQL 作业** | 中—高 | 逻辑改写工作量大，但可声明式化、可维护 |
| 实时点查（无明确实时仓） | **StarRocks 主键表 + 实时导入** | 中—高 | 对标 SEQ 的 GaussDB 实时补充 |

## 五、与华为 SEQ 的优劣势对比

### 5.1 逐维度对比

| 维度 | 华为 SEQ（CarbonData+Spark+Hetu+GaussDB） | 目标架构（Iceberg+StarRocks） | 占优 |
|------|----------------------------------------|------------------------------|------|
| **存储格式** | 私有 CarbonData，重索引、自带预聚合 | 开放 Iceberg + Parquet/ORC，标准化 | 各有侧重 |
| **详单高基数点查** | CarbonData 二级索引，开箱即用 | 需热冷分层/排序+Bloom/外置索引补齐 | **SEQ** |
| **多维统计查询** | Spark/Hetu（JVM） | StarRocks C++ 全向量化 | **目标** |
| **高并发交互式** | Hetu 中等 | StarRocks 强（向量化+缓存+MV） | **目标** |
| **时空查询** | CarbonData 时空索引（GeoHash/GeoSOT） | 无原生时空索引（WIP） | **SEQ** |
| **KPI 预聚合** | 内建 DataMap，自动路由 | 异步物化视图 + 透明重写（需自建） | 接近（实现方式不同） |
| **实时补充** | GaussDB（成熟企业级实时库） | StarRocks 主键表 + 实时导入 | 接近 |
| **计算编程模型** | Spark/SQL（湖内） | StarRocks SQL + MV（替代存储过程） | **目标**（去存储过程） |
| **资源复用/隔离** | 湖内统一 + 资源管控 | 湖仓统一 + 资源组隔离 | 接近（均优于现状） |
| **开放性/锁定** | 私有格式 + 华为生态绑定 | 开放标准 + 多引擎可读 | **目标** |
| **生态/演进速度** | CarbonData 社区弱化 | Iceberg/StarRocks 社区活跃、迭代快 | **目标** |
| **运维/人才** | 依赖华为体系 | 开源技能市场广 | **目标** |

### 5.2 目标架构相对 SEQ 的优势

1. **不锁定、开放标准**：Iceberg 被 Spark/Flink/Trino/StarRocks/Snowflake 等广泛支持，数据可被多引擎共享，规避私有格式（CarbonData）锁定与社区弱化风险。
2. **多维 + 高并发查询更强**：StarRocks C++ 全向量化 + Data Cache + 物化视图重写，在统计数据的交互式多维分析上普遍优于 Spark/Hetu（JVM）。
3. **用物化视图替代存储过程**：统计加工从"MPP 黑盒存储过程"变为"声明式 SQL + 异步物化视图"，可版本化、可测试、可迁移，**直接解决现状最痛的耦合问题**。
4. **湖仓真正统一**：详单与统计共用一份 Iceberg 存储 + 一套 StarRocks 算力，**资源弹性复用**，根治"两套存储 + 两套算力"的割裂。
5. **演进速度快**：加速能力沉在引擎，随 StarRocks 版本（Data Cache/MV/CBO/索引）持续增强，不受单一私有格式社区进度制约。

### 5.3 目标架构相对 SEQ 的劣势/风险

1. **详单点查能力需自建**：SEQ 靠 CarbonData 二级索引"白嫖"点查能力，目标架构必须工程化补齐（热冷分层/排序+Bloom/外置索引），这是**最大劣势与风险**。
2. **无原生时空索引**：若有网络覆盖/网格/`IN_POLYGON` 类时空分析，CarbonData 仍独占优势；Iceberg 地理空间能力 2026 初未 GA，需用分区/聚簇近似或外部方案。
3. **预聚合需自行设计维护**：CarbonData 的 Timeseries DataMap 是格式内建、查询自动路由；StarRocks 需为每类汇聚显式建并维护物化视图（Append-only 下增量刷新友好，是缓解点）。
4. **迁移工程量大**：自研格式 → Iceberg 的数据回灌、HBase 索引语义重建、MPP 存储过程改写，均非小工程。
5. **实时仓成熟度对标**：GaussDB 作为企业级实时库相对成熟；StarRocks 主键表高吞吐实时写入 + 大并发点查需充分压测调优。

> 客观结论：**在多维统计、开放性、计算解耦、资源复用上目标架构胜出；在详单点查与时空分析这两个 CarbonData "内建索引"强项上 SEQ 占优**。迁移的核心攻坚点正是把后者补齐到"可接受"水平。

## 六、下一步演进策略

### 6.1 演进总原则

1. **先易后难、先统计后详单**：统计场景迁移风险低、收益大，先做；详单点查是硬骨头，留待方案验证充分后再动。
2. **可行性先于全量迁移**：每阶段先 PoC + 基线对比（与现状/SEQ 同口径压测），用数据决策，再扩面。
3. **新老并行、灰度切换、可回退**：迁移期双写/双查对账，保留回退能力，杜绝"一刀切"。
4. **抽象存储访问层**：上层应用不直接耦合具体格式/引擎 API，为未来演进（Iceberg 索引 GA、引擎替换）预留弹性。

### 6.2 分阶段路线图

#### 阶段 0：评估与 PoC（地基）

- 建立 **基线压测口径**：详单点查（命中率/延迟/扫描量）、统计多维（并发/延迟/资源）、写入吞吐，分别对现状 MPP / 自研组件取基线。
- 搭建 Iceberg + StarRocks 试验环境，跑通：Iceberg 外表查询、Data Cache、异步物化视图、StarRocks 内表索引、实时导入。
- **重点验证详单点查方案**（4.3 的 A/B/C），用真实数据规模量化"点查退化"风险与补齐效果。

#### 阶段 1：统计数据先行迁移（速赢，解两大副作用）

- 统计明细落 **Iceberg**；高频 KPI 汇聚用 **StarRocks 异步物化视图**（透明重写 + 增量刷新）替代 MPP 存储过程。
- 用 **资源组** 在同一 StarRocks 集群隔离不同业务负载，实现**算力复用**。
- 灰度：先迁部分报表/多维场景，与 MPP 双跑对账，达标后扩面。
- **预期收益**：解除"资源隔离"与"存储过程耦合"，并把现状"详单不支持多维"通过统一 SQL 入口补上。

#### 阶段 2：XDR 详单入湖与点查攻坚

- 详单从自研格式回灌为 **Iceberg（Parquet/ORC）**，按 `event_time` + 点查键设计**分区与排序聚簇**，对点查列开 **Bloom Filter**。
- 落地**热冷分层**：近期热详单 → StarRocks 内表（带索引/主键表）；历史冷详单 → Iceberg 外表 + Data Cache；查询按时间窗口自动路由。
- 对必须的冷数据随机点查，保留**轻量 KV/HBase 索引**做兜底定位（过渡方案）。
- 灰度替换自研查询组件为 StarRocks SQL；逐步验证点查 SLA 达标。

#### 阶段 3：统一湖仓与下线

- 详单与统计统一在 Iceberg + StarRocks 之上；逐步**下线独立 MPP 集群与自研格式/查询组件**。
- 引入实时写入（StarRocks 主键表）对标 GaussDB 实时补充能力。
- 建立小文件 Compaction、快照过期、manifest 重写、物化视图刷新等**湖仓运维自动化**。
- 持续跟踪 Iceberg 二级索引/地理空间能力 GA，适时替换过渡性外置索引。

| 阶段 | 目标 | 主要风险 | 退出条件 |
|------|------|---------|---------|
| 0 | PoC + 基线 | 点查方案不达标 | 详单点查方案量化验证通过 |
| 1 | 统计迁移 | 物化视图覆盖不全 | 多维/并发达标 + 存储过程下线 |
| 2 | 详单入湖 | 点查退化 | 点查 SLA 达标 + 自研组件可替换 |
| 3 | 统一下线 | 实时/运维短板 | MPP + 自研格式安全下线 |

### 6.3 关键技术难点与对策

| 难点 | 风险 | 对策 |
|------|------|------|
| **详单高基数点查退化** | 最高 | 热冷分层（内表索引）+ 排序聚簇 + Bloom + Data Cache；冷数据保留 KV 兜底索引 |
| **MPP 存储过程改写** | 高 | 梳理过程逻辑→拆解为 SQL/物化视图；建立等价性对账测试 |
| **统计多维并发 SLA** | 中 | 物化视图预聚合 + 资源组隔离 + 缓存预热（CACHE SELECT） |
| **海量小文件/写放大** | 中 | Iceberg 定期 Compaction + 合理分区粒度 + 批量提交 |
| **实时写入吞吐** | 中 | StarRocks 主键表 + Routine/Stream Load 调优；必要时实时层独立 |
| **时空分析缺失** | 中（若有需求） | 分区/聚簇近似 + 外部时空方案；跟踪 Iceberg Geospatial GA |
| **迁移期一致性** | 中 | 双写双查对账 + 灰度 + 可回退 |

### 6.4 风险登记与回退预案

- **R1 详单点查不达标**：阶段 2 退出条件未满足时，详单维持现状（HBase+自研），仅统计迁移先收益；待 Iceberg 索引或方案成熟再推进。
- **R2 物化视图无法覆盖复杂加工**：保留少量 MPP/Spark 作业承接，分批改写，不强迁。
- **R3 实时能力不足**：实时点查场景过渡期保留专用实时层，待 StarRocks 实时方案压测达标再合并。
- **R4 资源/成本超预期**：分离存算（StarRocks Shared-Data）+ 对象存储控成本；按热度分层缓存。

## 七、结论与建议

1. **方向正确**：把存储与计算重心搬回湖中、用 **Iceberg + StarRocks** 开放栈替代自研格式/查询与独立 MPP，符合行业趋势，也与华为 SEQ 的"湖内存算"理念一致，且在**开放性、多维查询、计算解耦、资源复用**上优于现状与 SEQ。
2. **成败在详单点查**：整个迁移最大的技术风险是 **XDR 详单高基数点查在 Iceberg+StarRocks 上的裁剪能力**——这是 SEQ 靠 CarbonData 二级索引"内建"而目标架构必须"工程化补齐"的能力差。务必在 PoC 阶段用真实规模数据量化验证 **热冷分层 + 排序/Bloom + (兜底)外置索引** 的效果。
3. **策略是先统计后详单**：第一阶段迁统计数据即可解除"资源隔离 + 存储过程绑定"两大现状痛点并补上"详单不支持多维"短板，**收益快、风险低**；详单待点查方案验证充分后再动，全程灰度 + 可回退。
4. **客观看待与 SEQ 的差距**：在详单点查与时空分析上短期不及 SEQ 的 CarbonData 内建索引，需接受"用工程化补齐换开放与解耦"的权衡；但中长期随 StarRocks 引擎演进与 Iceberg 索引 GA，差距将收窄，而开放栈的生态与人才优势会持续放大。
