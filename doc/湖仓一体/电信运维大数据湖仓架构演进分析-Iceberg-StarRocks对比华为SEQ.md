## 一、问题陈述与核心结论

### 1.1 问题背景

电信运维大数据的两类核心数据：

- **XDR 详单**：会话级明细记录（S1-U/Gn/信令/话单等），单表数十亿~万亿行，日增 TB 级，典型查询是**按 IMSI/MSISDN/会话 ID 等高基数键的点查/明细回溯**。
- **XDR 统计数据**：由详单加工的多粒度汇聚指标（时间 × 区域 × 小区 × 网元 × KPI），数据量同样巨大，查询方式**多样、多维、并发要求高**（运维监控、KPI 报表、即席下钻）。

**我司现状**（架构定型于 2020 年前 Hadoop 生态早期）：

- 详单：**HBase 存索引 + 自研 HDFS 文件存储格式**，查询用**自研查询组件**（针对详单点查定制，**不支持多维查询**）。
- 统计：为满足多维 + 高并发，只能建设**规模巨大的 MPP 数据库集群**。

**两个突出副作用**：

1. **湖仓资源隔离、难以复用**：详单在 Hadoop 湖、统计在 MPP 仓，两套存储 + 两套算力，资源无法弹性互通。
2. **计算被 MPP 绑死**：统计数据之上的加工计算只能写在 **MPP 数据库的存储过程**里，逻辑与引擎强耦合、难维护、难迁移。

**华为对标产品 SEQ**：采用 **CarbonData + Spark + HetuEngine** 作为湖，**GaussDB 作为实时数据库补充**，核心的**存储、计算、查询均在湖内完成**——这正是"湖内存算一体"的形态。

**我司目标**：切换到 **Iceberg + Spark + StarRocks**，让**存储与计算的重心回到湖中**——其中 **Spark 作为湖内计算引擎**（承接现状 MPP 存储过程承担的统计加工）、**StarRocks 主要作查询引擎**（外表直读 Iceberg、**内表弱化**）。

> **目标架构与 SEQ 的结构同构**：调整后的目标栈（Iceberg + Spark + StarRocks）与华为 SEQ（CarbonData + Spark + HetuEngine + GaussDB）**形态高度对称**——都是"湖存储格式 + Spark 计算 + 查询引擎"。两者核心差异收敛为：① 存储格式（开放 Iceberg vs 私有 CarbonData）；② 查询引擎（StarRocks C++ 向量化 vs HetuEngine JVM）；③ 目标架构以 StarRocks 兼顾查询（弱化独立实时仓 GaussDB 的角色）。这意味着本次演进本质是"做一个开放栈版本的 SEQ"。

### 1.2 核心结论（先给答案）

| 问题 | 结论 |
|------|------|
| **技术可行性** | **整体可行，但需分场景**：统计数据场景**高度可行且收益最大**（Spark 做湖内加工写回 Iceberg + StarRocks 多维高并发查询，是各自主场）；XDR 详单**高基数点查**是**最大技术风险点**——Iceberg 无原生二级索引，且**StarRocks 内表弱化后无法把"内表索引"当主力**，故主线为"Spark 排序聚簇写入 + Bloom Filter + StarRocks Data Cache（外表）+ 外置 KV/二级索引兜底"。 |
| **vs 华为 SEQ 优势** | 与 SEQ **结构同构**（均为"湖格式 + Spark + 查询引擎"），但目标架构**存储格式开放不锁定**、**StarRocks C++ 全向量化在多维/高并发交互式查询上强于 HetuEngine（JVM）**、湖仓统一后**资源可弹性复用**、生态与演进速度更快。 |
| **vs 华为 SEQ 劣势** | SEQ 的 CarbonData 自带**二级索引 + 时空索引 + 内建预聚合**，详单点查与时空查询"开箱即用"；目标架构因 **Iceberg 缺这些内建能力 + 主动弱化 StarRocks 内表**，详单点查更依赖工程化补齐（外置索引兜底），实时仓能力也需评估。 |
| **演进策略（按实战修订）** | **详单已先行迁移、统计为当前攻坚**：① 详单先行（多维 XDR 查询是市场刚需）已迁至 Iceberg + StarRocks，**性能基本达标**；② **当前重点是统计数据迁移**——难在**数据量与加工作业量都极大**（大量 MPP 存储过程需批量改写为 Spark 作业、海量存量数据需回灌）；③ 最后统一下线 MPP 与自研残余。 |

**一句话**：方向正确——把存算重心搬回湖中（**Spark 算、StarRocks 查、Iceberg 存**）、用开放栈替代自研与 MPP；**详单已先行迁移、多维 XDR 查询基本达标，下一步真正的硬仗是把"数据量与加工作业量都极大"的统计数据迁过来**，核心是大量 MPP 存储过程向 Spark 作业的工程化改写与海量数据回灌。

```
            ┌──────────────────────────────────────┐
            │        分析 / 运维 / KPI 应用          │
            └───────────────┬──────────────────────┘
        ┌───────────────────┼───────────────────────┐
        │                                            │
┌───────▼────────┐                         ┌─────────▼─────────┐
│  HetuEngine    │   查询/联邦/下推         │   GaussDB(实时仓)  │
│ (交互式查询)   │                         │  实时数据库补充    │
└───────┬────────┘                         └─────────┬─────────┘
        │                                            │
┌───────▼────────┐   批处理/入湖/加工        ┌────────▼─────────┐
│     Spark      │◄────────────────────────►│  实时写入/点查    │
└───────┬────────┘                          └──────────────────┘
        │
┌───────▼────────────────────────────────────────────────────┐
│           CarbonData（湖内存储格式，自带索引）               │
│  多级索引 + 全局字典 + Sort/二级/时空索引 + 预聚合 DataMap   │
└───────┬─────────────────────────────────────────────────────┘
        │
┌───────▼────────────────────────────────────────────────────┐
│                HDFS / OBS（对象/分布式存储）                 │
└─────────────────────────────────────────────────────────────┘
```

- **存算重心在湖内**：CarbonData 把索引/预聚合内建进格式，Spark 负责批量加工与入湖，HetuEngine 负责交互式与联邦查询；存储、计算、查询都在湖里闭环。
- **GaussDB 仅作实时补充**：承接实时点查/低延迟场景，不是核心存储中心。
- **本质**：**私有重型存储格式 + 湖内闭环**。详单点查靠 CarbonData 二级索引，多维/时空靠多级索引与时空索引，KPI 汇聚靠内建预聚合——加速能力都"沉在格式里"。

### 2.2 我司现状：HBase 索引 + 自研 HDFS 格式 + 自研查询 + 大规模 MPP

```
   ┌─────────────────────┐         ┌──────────────────────────┐
   │   详单查询应用       │         │   统计/多维/报表应用      │
   │  (按用户/会话点查)   │         │  (多维 + 高并发)          │
   └─────────┬───────────┘         └─────────────┬────────────┘
             │                                    │
   ┌─────────▼───────────┐         ┌─────────────▼────────────┐
   │   自研查询组件       │         │     大规模 MPP 集群       │
   │ (详单定制,不支持多维)│         │  存储+计算+存储过程加工   │
   └─────────┬───────────┘         └─────────────┬────────────┘
             │                                    │ (独立存储,独立算力)
   ┌─────────▼───────────────────────────┐       │
   │  HBase 索引  +  自研 HDFS 文件格式   │       │
   └─────────┬───────────────────────────┘       │
             │                                    │
   ┌─────────▼────────────────────────────────────▼──────────┐
   │            两套独立体系，资源隔离、难以复用              │
   └──────────────────────────────────────────────────────────┘
```

- **详单侧**：HBase 维护点查索引（rowkey/二级映射），明细落在自研 HDFS 列式/行式文件；自研查询组件专为"按 key 取明细"定制——**点查高效，但不支持多维分析**。
- **统计侧**：为满足多维 + 高并发，独立建设大规模 MPP；统计加工逻辑写在 MPP **存储过程**中。
- **副作用根因**：详单（湖）与统计（仓）是**两套存储 + 两套算力**，无法弹性复用；加工计算与 MPP 引擎强绑定。

### 2.3 目标架构：Iceberg + Spark + StarRocks（湖内存算）

```
       ┌────────────────────────────┐   ┌──────────────────────────────┐
       │   ETL / 统计加工 / 回灌     │   │  详单点查 + 多维统计 + 即席下钻│
       └──────────────┬─────────────┘   └───────────────┬──────────────┘
                      │ 批计算/写回                       │ 标准 SQL(交互式)
       ┌──────────────▼─────────────┐   ┌───────────────▼──────────────┐
       │    Spark（湖内计算引擎）    │   │   StarRocks（查询引擎,C++向量化)│
       │  ETL/聚合/排序写入/Compact │   │  外表直读 Iceberg + Data Cache │
       │  替代 MPP 存储过程的加工    │   │  + 物化视图重写 + 资源组隔离   │
       │                            │   │  内表(主键/索引)：弱化、按需   │
       └──────────────┬─────────────┘   └───────────────┬──────────────┘
                      │ 读写                External Catalog│ (外表,零搬运)
       ┌──────────────▼───────────────────────────────────▼──────────────┐
       │                Iceberg（开放表格式 / 统一表层）                   │
       │   metadata/manifest 裁剪 + 隐藏分区 + 排序聚簇 + Bloom/Puffin     │
       │   数据文件: Parquet/ORC                                          │
       └──────────────────────────────┬──────────────────────────────────┘
                                      │
       ┌──────────────────────────────▼──────────────────────────────────┐
       │                  HDFS / S3 / OSS（统一对象存储）                  │
       └───────────────────────────────────────────────────────────────────┘
```

- **存算重心回湖、职责清晰**：一份 Iceberg 数据，**Spark 负责"算"**（ETL、统计加工、排序聚簇写入、Compaction，替代 MPP 存储过程）、**StarRocks 负责"查"**（外表直读 Iceberg，交互式多维/点查）、**Iceberg 负责"存"**；详单与统计共享同一存储与算力池。
- **StarRocks 内表弱化**：StarRocks 主用作查询引擎，**不把数据沉淀进内表作为主存**；内表仅在"极热小窗口需要极致点查/实时"等必要场景按需、最小化使用。
- **加速重心在引擎**：StarRocks 用 Data Cache、物化视图、向量化承担查询加速；Spark 通过排序写入/Compaction 优化 Iceberg 的裁剪率；Iceberg 提供精准元数据做文件裁剪。
- **本质**：**开放轻量表格式 + Spark 计算 + 强向量化查询引擎 + 统一湖仓**——与 SEQ 的"湖内闭环（CarbonData+Spark+Hetu）"**结构同构**，但用开放格式 + StarRocks 替代私有格式 + HetuEngine。

## 三、现状架构的根因剖析与副作用

### 3.1 为什么会形成现状（历史合理性）

| 现状选择 | 当年（2020 前）原因 | 当时的合理性 |
|---------|-------------------|------------|
| HBase 存索引 | 早期 Hadoop 缺少成熟列存表格式（Iceberg 2017 起步、当时未成熟），HBase 是最现实的高基数点查方案 | 合理 |
| 自研 HDFS 文件格式 | Parquet/ORC 当时对电信明细的压缩/裁剪不够理想，CarbonData 属华为私有 | 合理（但埋下锁定隐患） |
| 自研查询组件（仅点查） | 业务首要诉求是详单回溯，多维分析需求尚未爆发 | 合理（但欠缺扩展性） |
| 独立大规模 MPP | 当时湖上引擎（Hive/早期 Presto）无法满足统计的多维 + 高并发 + 低延迟 | 合理（但造成湖仓割裂） |

**关键判断**：现状不是"设计失误"，而是**时代局限下的合理选择**。但随着开放表格式（Iceberg）与向量化湖上引擎（StarRocks）成熟，这些选择的**技术债已显性化**。

### 3.2 现状的核心副作用（迁移要解决的目标）

| 副作用 | 表现 | 业务/工程代价 |
|--------|------|--------------|
| **湖仓割裂、资源不可复用** | 详单（HDFS+HBase）与统计（MPP）两套存储 + 两套算力 | 资源利用率低、扩容各自为政、成本高 |
| **计算与 MPP 强耦合** | 统计加工只能写 MPP 存储过程 | 逻辑黑盒、难测试、难迁移、人才依赖 |
| **详单不支持多维** | 自研查询组件仅按 key 取明细 | 多维分析需把数据再倒进 MPP，链路冗长、时效差 |
| **自研格式/组件维护成本** | 私有格式与查询组件需自行长期维护 | 团队负担重、生态隔离、招聘困难 |
| **数据多副本** | 同源数据在 HDFS、HBase、MPP 多处存储 | 存储浪费、一致性风险 |

## 四、两条路线对比：第一性原理拆解（V1.1）

> **V1.1 说明**：旧版（现 4.5–4.8）按"存储格式 / 查询效率 / 加速方式"逐项罗列特性，信息全但**重点难抓**——每个特性背后都有一串技术支撑，读起来生涩。本节（4.1–4.4）改用**第一性原理**自顶向下拆解：先把几十种特性还原到**两个根本因子**，再锁定两条路线**唯一真正的分野**和**判断胜负的唯一变量**，最后一眼落到电信运维。**只读 4.1–4.4 即可把握全部要点**，4.5–4.8 作为特性展开备查。

### 4.1 第一性原理：OLAP 性能只由两个因子决定

抛开所有产品特性，任何分析型查询的耗时，本质都可写成：

```
查询耗时 ≈  需要处理的数据量  ÷  处理数据的速度
          └──── 读得少 ────┘   └──── 算得快 ────┘
```

于是所有性能问题被还原为两个可独立优化的因子：

1. **读得少（Data Skipping / 裁剪）**：在海量数据中只读"与本次查询相关"的极小部分、跳过其余。决定它的，是系统**能多精确地知道"哪些数据不用读"**——靠元数据/索引（分区、min-max、二级索引、时空编码……）。
2. **算得快（Execution）**：对真正读进来的数据，单位时间能处理多少行。决定它的，是**引擎 CPU 效率（向量化/SIMD/编码）+ 数据离计算有多近（缓存/本地性）**。

**第一性原理一句话**：所有加速手段——索引、字典、分区、Bloom、缓存、向量化、物化视图……——本质都只在做两件事之一：**要么让你"少读"，要么让你"快算"**。把令人眼花的特性按这两个因子归位，比较立刻清晰：

| 常见特性 | 本质归位 |
|---------|---------|
| 分区裁剪、min/max、Bloom Filter、二级索引、时空索引 | **少读** |
| 列存、字典编码、向量化/SIMD、Data Cache、数据本地性 | **快算** |
| 物化视图 / 预聚合 | **两者兼有**（既减少要算的数据量，又把结果预先算好） |

### 4.2 核心分野：把"少读的智能"铸进数据还是交给引擎

有了两个因子，就能一眼看出两条路线**唯一真正、且无法互相速成的分野**——它不在"快算"（两者都能上向量化，StarRocks 已是 C++ 全向量化，差距可被引擎升级抹平），而在 **"少读"的能力建在哪一层、以什么粒度**：

- **CarbonData 路线 = 把"少读的智能"铸进数据本身**。写入时就把多级索引、二级索引、排序聚簇、时空编码"长"在文件里；于是"哪些数据不用读"，**数据自己就知道，粒度细到 Blocklet/Page**。代价：这套智能**私有、重、随格式锁定、演进慢**。
- **Iceberg + StarRocks 路线 = 把"少读"做薄、把"快算 + 缓存"做厚**。Iceberg 只保留**文件级**粗裁剪（分区 / manifest min-max），把精细"少读"让位给**开放与轻量**；StarRocks 用极致"快算"（C++ 向量化）+ **把数据搬到离计算最近处**（Data Cache）+ **预先算好**（物化视图）来补偿。代价：对"本应大幅少读"的查询，**粗裁剪 + 快算救不回来**。

> **最核心的一句话**：**CarbonData 赌"把数据读少"（智能入数据）；Iceberg + StarRocks 赌"把数据算快、缓存近"（智能入引擎）。** 这是两条路线唯一的本质分野，其余所有特性差异都是这一选择的派生结果。

### 4.3 决定胜负的唯一判断点：查询的"可裁剪性"

既然分野是"少读 vs 快算+缓存"，那么对任意一条查询，**谁更优只取决于一个量：这条查询有多少数据是"本可以不读"的——即它的"可裁剪性 / 选择性"。**

| 查询的可裁剪性 | 瓶颈在 | 谁赢 | 为什么 |
|--------------|-------|------|-------|
| **高**（选择性极高、裁剪键能被索引精确命中，万里挑一） | 读 | **少读路线（CarbonData）** | 只需读极小部分；再快的引擎也架不住把不该读的也读了 |
| **低**（大范围扫描型聚合，本来就要读很多） | 算 | **快算路线（StarRocks）** | 可跳过的数据有限，胜负转移到引擎吞吐 |
| **中**（介于两者之间） | 读 + 算 | 看工程 | 用分区 + 排序聚簇 + Bloom + 缓存把可裁剪性"工程化拉高"，让快算路线逼近少读路线 |

> **判断口诀**：**先问"这条查询能裁掉多少数据"**——能裁掉绝大部分 → 该靠"少读"（索引/格式）；裁不掉多少 → 该靠"快算"（引擎/缓存）。不必纠结谁的特性更多。

### 4.4 落到电信运维：用一个核心点看穿全局

把 4.1–4.3 套到电信运维的几类典型查询上，全文结论瞬间自洽：

| 电信典型查询 | 可裁剪性 | 本质赢法 | 主场 | 现实印证 |
|------------|---------|---------|------|---------|
| **详单高基数点查**（按 IMSI/会话 ID 取明细） | 极高（万里挑一） | 少读 | CarbonData/SEQ | 正是它在 Iceberg+StarRocks 上最难的**根因**；解法＝用外置索引/排序聚簇把"少读"补回来 |
| **详单 / 统计多维聚合**（time×region×小区×KPI） | 低（大范围扫描） | 快算 | StarRocks | 正是**详单多维已实战达标、统计查询不愁**的根因 |
| **时空范围查询**（覆盖/网格/`IN_POLYGON`） | 高（空间局部性） | 少读 | CarbonData | Iceberg 无时空索引，需聚簇近似或外部方案 |

由此，全文三大结论都从这一个核心点自然导出：

1. **详单点查是难点**——不是"StarRocks 不行"，而是这类查询的赢法是"少读"，而开放栈天生把"少读"做薄了；**对策必然是把"少读"以外置索引/排序聚簇补回来**（→ 第五章 5.3）。
2. **统计迁移查询侧不愁**——多维聚合的赢法是"快算"，正是 StarRocks 主场；**统计迁移的真正难点不在查询，而在工程**（海量回灌 + 大量存储过程改写，→ 第七章）。
3. **与 SEQ 的取舍**——SEQ（CarbonData）在"少读型"查询（点查/时空）占优，目标架构在"快算型"查询（多维）与开放性占优；选型本质是"哪类查询是你的主战场"（→ 第六章）。

> **一句话总纲**：**看一条查询能否"裁掉绝大部分数据"，即可判断它该靠"少读"还是"快算"——这是贯穿全文可行性、对比与策略的唯一主线。** 下面 4.5–4.8 的三维度特性表，只是这条主线的展开与佐证，可按需查阅。

---

> **以下 4.5–4.8 为三维度特性的详细展开**（对应 4.1 的"少读 / 快算"归位），供需要技术细节时查阅；只想抓重点者可跳过。

### 4.5 详细展开：设计哲学（加速沉到存储 vs 沉到引擎）

两条路线最根本的差异，是**把加速能力放在哪一层**（即 4.2 的"少读智能放在数据还是引擎"在工程层面的体现）。

> 注：**Spark 是两条路线共同的批计算引擎**（SEQ 与目标架构都用 Spark 做 ETL/加工/写入），因此它不构成路线差异；真正的差异集中在**存储格式（CarbonData vs Iceberg）**与**查询引擎（HetuEngine vs StarRocks）**两层，下表与本章后续即围绕这两层展开。

| 视角 | CarbonData + HetuEngine（SEQ 路线） | Iceberg + StarRocks（目标路线） |
|------|----------------------------------|------------------------------|
| **设计哲学** | 重存储：把加速能力内建进文件格式 | 重引擎：表格式只管"表的元数据与事务"，加速交给引擎 |
| **格式角色** | 文件格式 + 表语义 + 索引 三合一 | 表格式（元数据层）与文件格式（Parquet/ORC）解耦 |
| **批计算引擎** | Spark（共同） | Spark（共同） |
| **查询引擎角色** | HetuEngine：联邦虚拟化（JVM，Trino/Presto 系） | StarRocks：极速向量化 MPP（C++，外表挂载 Iceberg） |
| **加速位置** | 存储格式内建（索引/字典/预聚合） | 计算引擎承担（缓存/物化视图/向量化） |
| **耦合度** | 格式与引擎强耦合（CarbonData 主要被 Spark/Hetu 读） | 松耦合（Iceberg 被几乎所有引擎读写） |
| **开放性** | 私有格式，生态收窄 | 开放标准，生态最广 |
| **加速演进** | 受 CarbonData 社区活跃度限制（较慢） | 随 StarRocks 引擎版本快速迭代（快） |

**一句话**：CarbonData 把加速"打进文件里"，一次写入随数据移动、跨引擎复用，对只读/多维/时空场景近乎开箱即用，但格式重、写入慢、演进受限、社区弱；Iceberg 把表格式做薄、保持开放，加速交给 StarRocks 承担，更易随引擎升级持续增强、且数据可被多引擎共享，代价是加速效果依赖具体引擎（且当内表弱化时，详单点查这类强依赖索引的能力更需工程化补齐）。

### 4.6 详细展开：存储格式（CarbonData vs Iceberg）

#### CarbonData：列存文件格式 + 重型内建索引

CarbonData 是"一个文件格式同时承担文件编码、索引、表语义、预聚合"四重职责的私有列存格式。

- **多级索引**：物理布局 `Segment → CarbonData File → Blocklet(≤64MB) → Page`，配合独立 `.carbonindex` 维护 Block/Blocklet/Page **多级 min/max 索引**；相比 Parquet 仅 RowGroup 级、ORC 仅 Stripe 级统计，裁剪粒度更细，高选择性查询实际读取量常降 1–2 个数量级。
- **全局字典编码 + 延迟物化**：低基数列编码为整型，压缩率约 60%–80%，GROUP BY/聚合直接在编码上执行、仅最终解码。
- **Sort Columns 聚簇**：按业务查询模式排序落盘，强化 min/max 裁剪。
- **二级索引**：对高基数列（如 MSISDN）建辅助索引，支持**高基数点查**，避免全扫。
- **时空索引**：基于 GeoHash/GeoSOT 空间填充曲线，把空间相邻数据排布相邻，原生支持 `IN_POLYGON`（Iceberg/Parquet 截至 2026 初仍不具备生产可用能力）。
- **内建预聚合（Timeseries/Pre-agg DataMap）**：把"指标层/汇聚表"内建进格式，查询自动路由到最优预聚合（SQL 零改造）。
- **短板**：事务/并发弱（以 Segment 批次管理，IUD 能力有限、写放大大）、Schema 演进有限、基本无 Time Travel、生态收窄（主要绑定 Spark/Hetu）。

#### Iceberg：表格式（Table Format）+ Parquet/ORC 数据文件

Iceberg 把"表是什么"抽象为一层独立元数据，数据文件本身仍是标准 Parquet/ORC/Avro。

- **三层元数据**：`metadata.json → manifest list → manifest（含每个数据文件的分区值与列级 min/max/null/记录数）→ data/delete file`；查询可只读清单完成**文件级裁剪**，避免对象存储昂贵的 LIST。
- **隐藏分区**：通过分区变换（`days/bucket/truncate/...`）在元数据层维护分区，查询无需显式分区谓词即可裁剪，且支持分区演进而不重写历史。
- **Schema 演进**：基于列 ID（field-id），支持加/删/改名/重排/类型提升，历史数据不重写。
- **快照 / Time Travel / ACID**：每次写入生成新 snapshot，读写隔离，支持时间回溯与回滚，乐观并发提交。
- **行级更新**：Copy-on-Write（读快写慢）/ Merge-on-Read（写快读时合并 delete file）。
- **统计**：Puffin 文件存列级 NDV 等统计供 CBO；数据文件级有 Parquet/ORC 的 RowGroup/Stripe 统计 + 字典 + 可选 Bloom Filter。
- **短板**：**无内建细粒度/二级/时空索引、无内建预聚合**（裁剪靠 manifest + 文件级统计，粒度粗于 CarbonData；预聚合需引擎物化视图）；高频写入产生小文件与元数据膨胀，需 Compaction / expire snapshots / rewrite manifests 维护。

#### 存储格式维度对比表

| 能力 | CarbonData | Iceberg（+ Parquet/ORC） |
|------|-----------|--------------------------|
| **本质** | 文件格式 + 索引 + 表语义 三合一 | 表格式（元数据层），数据文件用 Parquet/ORC |
| **索引粒度** | Block/Blocklet/Page 多级（细） | manifest 文件级 + RowGroup/Stripe 级（较粗） |
| **二级索引（高基数点查）** | ✅ | ❌（依赖文件统计 + 可选 Bloom Filter） |
| **时空索引** | ✅ GeoHash/GeoSOT + `IN_POLYGON` | ❌（WIP，2026 初未 GA） |
| **内建预聚合** | ✅ DataMap（自动路由） | ❌（需引擎物化视图） |
| **Schema 演进** | 有限 | ✅ 基于 field-id，历史不重写 |
| **分区** | 静态分区 + Sort Columns | ✅ 隐藏分区 + 分区变换 + 分区演进 |
| **快照 / Time Travel / ACID** | ❌/弱（Segment 批次） | ✅ snapshot 隔离 + 回溯 + 乐观并发 |
| **行级更新** | 弱（IUD，写放大大） | ✅ COW / MOR |
| **统计信息** | 内建多级 min/max | ✅ manifest 列级统计 + Puffin（NDV） |
| **跨引擎开放性** | 弱（Spark/Hetu 为主） | ✅ 极广（Spark/Flink/Trino/StarRocks/...） |
| **适配负载** | 只读 / 多维 OLAP / 时空 / 高基数点查 | 通用湖仓 / 演进频繁 / 事务更新 / 跨引擎共享 |

### 4.7 详细展开：查询效率（HetuEngine vs StarRocks）

#### HetuEngine 查询 CarbonData 的执行链路

```
SQL → HetuEngine Coordinator（解析/优化/分片，谓词/投影/聚合下推）
        → HetuEngine Worker（JVM 分布式执行）
              → CarbonData Connector 读取
                    → Block/Blocklet/Page 索引裁剪 + 字典上聚合 + 延迟物化
                          → HDFS/OBS
```

- **裁剪靠存储格式**：Hetu 把谓词推给 CarbonData，由其多级/二级/时空索引完成裁剪——越命中索引列，扫描量下降越显著。
- **JVM 执行**：源自 Trino/Presto，向量化程度低于原生 C++ 引擎；但分布式 pipeline、计算下推、CTE/元数据缓存成熟。
- **联邦是亮点**：可跨源关联（CarbonData ⨝ Hive/HBase/GaussDB），代价是联邦性能上限低于单引擎本地执行。
- **典型增益**：CarbonData 相比原生 SparkSQL 约 10x（格式贡献）；Hetu 跨源下推相比开源约 5x（引擎贡献）。

#### StarRocks 查询 Iceberg 的执行链路

```
SQL → StarRocks FE（解析/CBO（用 manifest+Puffin 统计）/物化视图重写/调度，文件级裁剪）
        → StarRocks BE/CN（C++ 全向量化 MPP + SIMD）
              → Data Cache（内存 L1 → NVMe L2）命中则本地读
                    → miss：Iceberg 数据文件（Parquet/ORC，RowGroup/Stripe 裁剪 + 列裁剪）
                          → HDFS/S3/OSS
```

- **C++ 全向量化 + CBO**：列式内存 + SIMD，交互式延迟与 CPU 效率优于 JVM；FE 用 Iceberg manifest/Puffin 统计做代价优化。
- **本地 Data Cache**：把远程文件块缓存到本地内存/NVMe，命中时接近内表性能，弥补存算分离 IO 短板。
- **物化视图查询重写**：异步 MV 对 Iceberg 表预计算，查询自动重写命中（等价"引擎侧预聚合"）。
- **外表零导入**：External Catalog 直读 Iceberg，无需 ETL 入库；冷查询（缓存未命中）受对象存储带宽/延迟限制。
- **典型增益**：行业实践中 StarRocks 查询湖表性能可达 SparkSQL 的 3–8x。

#### 查询效率维度对比表

| 维度 | HetuEngine + CarbonData | StarRocks + Iceberg |
|------|------------------------|---------------------|
| **执行内核** | JVM，Trino/Presto 系 | C++ 全向量化 MPP + SIMD |
| **数据裁剪主力** | CarbonData 多级/二级/时空索引（细） | Iceberg manifest + 文件级统计（较粗） |
| **本地数据块缓存** | 弱（以 CTE/元数据缓存为主） | ✅ Data Cache（内存 + NVMe，默认开启，SLRU） |
| **交互式低延迟 / 高并发** | 中 | **高**（向量化 + 缓存 + MV 重写） |
| **多维 / 时空 / 高基数点查** | **强**（格式内建索引/预聚合） | 中（无内建二级/时空索引，靠扫描 + MV 弥补） |
| **跨源联邦关联** | **强**（Hetu 原生） | 中（JDBC/多 Catalog） |
| **更新表 / Schema 演进表分析** | 弱 | 高（Iceberg MOR + field-id 演进） |

#### 典型负载下的效率画像

| 查询负载 | HetuEngine + CarbonData | StarRocks + Iceberg | 更优 |
|---------|------------------------|---------------------|------|
| 交互式 BI 仪表盘（亚秒级） | 中 | 高 | **B** |
| 多维 OLAP 聚合 | 高（Sort + 多级索引 + 预聚合） | 高（向量化 + MV，无内建预聚合） | A≈B |
| 时空 / 多边形查询 | **高**（时空索引） | 低—中（无时空索引） | **A** |
| 高基数点查（按用户/ID） | 中—高（二级索引） | 中（无二级索引，靠文件统计/Bloom） | **A** |
| 跨源关联（湖 ⨝ 业务库） | **高**（Hetu 联邦） | 中 | **A** |
| 频繁更新 / CDC 表分析 | 低（IUD 弱） | 高（MOR + 读合并） | **B** |
| Schema 频繁演进的表 | 低 | 高（field-id 演进） | **B** |

> 注：上表中 A = CarbonData + HetuEngine，B = Iceberg + StarRocks。

### 4.8 详细展开：加速方式

两条路线的加速哲学根本不同：**A 把加速"沉到存储格式"，B 把加速"沉到计算引擎"。**

#### A（CarbonData + HetuEngine）的加速手段

- **存储格式侧（主力）**：① 多级索引裁剪（Block/Blocklet/Page）；② 全局字典编码 + 延迟物化；③ Sort Columns 聚簇；④ 二级索引（高基数点查）；⑤ 时空索引（GeoHash/GeoSOT，`IN_POLYGON`）；⑥ Timeseries/Pre-agg DataMap 内建预聚合（自动路由）。
- **计算引擎侧（辅助）**：⑦ 计算下推（谓词/投影/聚合/子查询，复用源端索引）；⑧ CTE 缓存；⑨ 元数据缓存；⑩ 物化视图（能力弱于 StarRocks 的查询重写体系）。

#### B（Iceberg + StarRocks）的加速手段

- **计算引擎侧（主力）**：① Data Cache（1MB Block 为单元，内存 L1 + NVMe L2，v3.3 默认开启，SLRU 防污染）；② 缓存预热 `CACHE SELECT`；③ 自适应缓存填充（v3.3.2+）；④ 一致性哈希 Scan Range 调度（最大化命中）+ 增量 Scan Range 部署；⑤ 异步物化视图 + 透明查询重写（分区级增量刷新）；⑥ 全向量化执行 + CBO。
- **存储格式侧（辅助）**：⑦ manifest 文件级裁剪；⑧ 隐藏分区裁剪；⑨ Puffin 统计（NDV）供 CBO；⑩ Parquet/ORC 的 RowGroup/Stripe 裁剪、列裁剪、字典、可选 Bloom Filter；⑪ Compaction / 排序写入（含 Z-order/Hilbert 聚簇，引擎侧）提升后续裁剪率。

#### 加速方式维度对比表

| 加速手段 | A：CarbonData + HetuEngine | B：Iceberg + StarRocks |
|---------|----------------------------|------------------------|
| **加速重心** | 存储格式（索引/字典/预聚合内建） | 计算引擎（缓存/物化视图/向量化） |
| **数据块缓存** | 弱 | ✅ Data Cache（内存+NVMe，默认开启） |
| **缓存预热** | ❌ | ✅ CACHE SELECT |
| **细粒度 / 二级 / 时空索引** | ✅（多级 + 二级 + 时空） | ❌（文件级统计 + 可选 Bloom） |
| **内建预聚合** | ✅ DataMap（自动路由） | ❌（用引擎物化视图替代） |
| **物化视图 + 查询重写** | 一般（Hetu MV） | ✅ 异步 MV + 透明重写 + 增量刷新 |
| **计算/谓词下推** | ✅ Hetu 下推 + 格式索引过滤 | ✅ 谓词/分区/列裁剪下推到文件层 |
| **CBO 统计** | CarbonData 元数据 | ✅ manifest 统计 + Puffin NDV |
| **加速随版本演进** | 受 CarbonData 社区限制（慢） | ✅ 随 StarRocks 迭代（快） |
| **加速可移植性** | 高（随数据/格式走，跨引擎复用） | 中（核心加速绑定 StarRocks，元数据通用） |

## 五、目标架构（Iceberg + Spark + StarRocks）技术可行性分析

### 5.1 总体可行性判断

| 子场景 | 可行性 | 关键依据 | 主要风险 |
|--------|-------|---------|---------|
| **统计数据多维 + 高并发查询** | **高** | StarRocks C++ 全向量化 + 物化视图 + Data Cache，正是其主场 | 低（成熟方案） |
| **统计加工计算（去 MPP 存储过程）** | **高** | 用 **Spark on Iceberg 批作业**承接加工，写回 Iceberg；逻辑声明式化 | 中（存储过程逻辑改写工作量） |
| **详单多维查询（已先行迁移）** | **高（实战已达标）** | 详单已迁入 Iceberg + StarRocks，多维 XDR 查询性能基本达标 | 低（已验证） |
| **详单高基数随机点查（剩余子风险）** | **中** | Iceberg 无原生二级索引、内表弱化；靠 Spark 排序 + Bloom + Data Cache，冷随机点查用外置索引兜底 | 中（仅冷随机点查） |
| **湖仓统一/资源复用** | **高** | 单一 Iceberg 存储 + Spark/StarRocks 共用对象存储与算力 + 资源组隔离 | 低 |
| **实时写入/实时查询** | **中** | StarRocks 主键表可用但**内表弱化**，真正实时场景需谨慎设计或保留轻量实时层 | 中（与内表弱化定位的取舍） |

### 5.2 统计数据场景：可行性高

统计数据的诉求拆成"加工"与"查询"两段，分别由 Spark 与 StarRocks 承接，正好各取所长：

- **加工去存储过程（Spark 主力）**：把 MPP 存储过程里的汇聚/派生逻辑改写为 **Spark on Iceberg 批作业**（或 Spark SQL），结果写回 Iceberg 统计表。逻辑从"MPP 黑盒存储过程"变为"可版本化、可测试、可调度的 Spark 作业"，且与现状/SEQ 的 Spark 技能栈一致，迁移摩擦小。
- **多维查询（StarRocks 主力）**：StarRocks 外表直读 Iceberg 统计表，C++ 全向量化 + SIMD + CBO（基于 manifest 统计与 Puffin NDV）支撑多维过滤聚合；高并发短查询配合 **Data Cache** 与 **资源组（Resource Group）负载隔离**。
- **查询侧加速（按需，非主存）**：对高频固定汇聚，可用 **StarRocks 异步物化视图 + 透明重写**（Append-only 下增量刷新友好）做查询加速——这属于"查询引擎的可选加速"，**不等同于把数据沉淀进内表**，与"内表弱化"定位不冲突。
- **湖内存算**：统计明细与汇聚表都以 Iceberg 承载，Spark 算、StarRocks 查，**存储与计算回到湖内统一栈**。

> 结论：统计场景**技术风险低、收益大**（详单已先行迁移达标，统计是当前主战场）——**Spark 接管加工即可解除"存储过程绑定"，StarRocks 统一查询 + 资源组即可解除"资源隔离"**两大副作用。但需清醒认识：**技术可行 ≠ 工程轻松**，统计迁移的真正挑战在于**数据量与加工作业量都极大**（海量回灌 + 大量存储过程改写），这是一场重工程量的攻坚（详见第七章）。

### 5.3 XDR 详单场景：多维查询已实战达标，点查为剩余子风险

> **实战进展（2026，重要）**：因**多维 XDR 查询是市场刚需**，详单已**先行一步**迁移至 **Iceberg + StarRocks**，**多维查询性能基本达标**。即本节原先判定的"详单为最大风险"，在多维查询维度上**已被实战验证可行**；本节分析转为该迁移的**经验沉淀**，并继续指导"高基数随机点查（冷数据）"这一**剩余子风险**的兜底设计。

这是详单迁移的技术核心。详单的核心查询除多维分析外，还包括**数十亿行中按高基数键（IMSI/MSISDN/会话 ID）点查明细**，而（呼应第四章原理）：

- **现状**：HBase 索引天然适合高基数点查（按 rowkey/二级索引毫秒级定位）。
- **SEQ**：CarbonData 自带**二级索引**，点查"开箱即用"。
- **Iceberg + StarRocks 外表**：**Iceberg 无原生二级索引**；文件级 min/max 统计对**高基数随机值几乎无裁剪效果**（min/max 区间覆盖全域），即使叠加 Parquet/ORC **Bloom Filter** 也只能做**文件级**过滤，粒度粗于 HBase/CarbonData，存在**点查退化为大范围扫描**的风险。

> **内表弱化带来的额外影响**：在"StarRocks 内表作为主力点查载体"的设计下，本可用"热数据进内表 + 内表二级/前缀/倒排索引"获得接近 HBase 的点查体验；但本目标架构**主动弱化内表**，意味着**不能把内表索引当主力兜底**——详单点查必须主要在 **Iceberg（外表）侧**解决。这使得点查风险**比"内表可用"时更高**，**外置索引兜底（方案 C）的必要性显著上升**。

**可行的补齐方案（结合"内表弱化"重新排序）**：

| 方案 | 机制 | 适用 | 代价/限制 |
|------|------|------|----------|
| **B. Spark 排序聚簇写入 + Bloom Filter（推荐主线）** | Spark 入湖时按点查键 **sort/bucket 聚簇** + 对点查列建 **Bloom Filter**；StarRocks 外表查询 + **Data Cache** 加速重复访问 | 点查键与排序/分桶键相关性高、可预测 | 一份数据只能按一组键聚簇；纯随机高基数键裁剪有限；写入有排序成本 |
| **C. 外置 KV/二级索引兜底（内表弱化下权重上升）** | 保留/新建轻量 KV 索引（继续用 HBase 或换 KV）做"高基数键 → Iceberg 文件/分区"定位，再由 StarRocks/Spark 精准读取命中文件 | 冷数据、纯随机高基数点查 | 引入额外组件，局部回到"索引 + 存储"分离；需维护索引与数据一致性 |
| **A. StarRocks 内表（仅限定、按需，非主线）** | 仅对**极热小窗口**（如最近数小时）的详单放内表 + 索引以满足极致点查/实时 | 少量超热数据 | **与"内表弱化"定位冲突，须严格控制规模**，不作为通用兜底 |
| **D. 跟踪 Iceberg 二级索引/删除向量演进** | Iceberg 社区正推进文件级索引能力 | 中长期 | 2026 初尚未 GA，不能作为当期依赖 |

> 现实建议：**B（Spark 排序聚簇 + Bloom + Data Cache）为主线 + C（外置 KV 索引）为冷数据随机点查的兜底**；A（内表）仅在极热小窗口按需、严格限量使用。实战中详单多维查询已基本达标，**剩余需持续打磨的是"冷数据纯随机高基数点查"**——对该类查询应以 C（外置索引）兜底，避免退化为大范围扫描。

### 5.4 组件级迁移映射与可行性

| 现状组件 | 目标组件 | 迁移可行性 | 说明 |
|---------|---------|-----------|------|
| 自研 HDFS 文件格式 | **Iceberg + Parquet/ORC** | 高 | 标准化、跨引擎，去自研维护负担；需 Spark 做数据格式转换/回灌 |
| 详单加工 / ETL / 入湖 | **Spark on Iceberg** | 高 | Spark 为湖内计算引擎，负责排序聚簇写入、Compaction |
| HBase 详单索引 | **Iceberg 排序/Bloom + Data Cache（主）+ 外置 KV 兜底；StarRocks 内表仅极热按需** | 中 | 因**内表弱化**，高基数点查以 Iceberg 侧 + 外置索引为主（见 5.3） |
| 自研查询组件（仅点查） | **StarRocks SQL** | 高 | 统一 SQL 入口，且天然支持多维查询（补齐现状短板） |
| 统计 MPP 集群（存储+计算） | **Iceberg 存储 + Spark 计算 + StarRocks 查询** | 高 | 加工归 Spark、查询归 StarRocks，职责分离 |
| MPP 存储过程 | **Spark 批作业 / Spark SQL（主）+ 可选 StarRocks 物化视图（查询加速）** | 中—高 | 逻辑改写工作量大，但可声明式化、可维护、与现有 Spark 技能一致 |
| 实时点查（无明确实时仓） | **StarRocks 查询为主；真正实时按需用主键表（弱化）或保留轻量实时层** | 中 | 内表弱化下不依赖大规模主键表对标 GaussDB |

## 六、与华为 SEQ 的优劣势对比

> 本章是第四章机制对比在 **SEQ 产品语境**下的应用结论：把"CarbonData + HetuEngine"具体化为华为 SEQ（含 GaussDB 实时补充），与目标架构对照（机制原理详见第四章）。
>
> **结构同构提示**：目标架构（Iceberg + **Spark** + StarRocks）与 SEQ（CarbonData + **Spark** + HetuEngine + GaussDB）形态对称——**批计算都用 Spark**，差异集中在 ① 存储格式（开放 Iceberg vs 私有 CarbonData）、② 查询引擎（StarRocks vs HetuEngine）、③ 目标架构用 StarRocks 兼顾查询、弱化独立实时仓（GaussDB）。因此本对比可聚焦这三点。

### 6.1 逐维度对比

| 维度 | 华为 SEQ（CarbonData+Spark+Hetu+GaussDB） | 目标架构（Iceberg+Spark+StarRocks） | 占优 |
|------|----------------------------------------|------------------------------|------|
| **存储格式** | 私有 CarbonData，重索引、自带预聚合 | 开放 Iceberg + Parquet/ORC，标准化 | 各有侧重 |
| **批计算引擎** | Spark | Spark | 相同 |
| **详单高基数点查** | CarbonData 二级索引，开箱即用 | 需 Spark 排序+Bloom+外置索引补齐（**内表弱化**，不靠内表索引兜底） | **SEQ** |
| **多维统计查询** | HetuEngine（JVM） | StarRocks C++ 全向量化 | **目标** |
| **高并发交互式** | Hetu 中等 | StarRocks 强（向量化+缓存+MV） | **目标** |
| **时空查询** | CarbonData 时空索引（GeoHash/GeoSOT） | 无原生时空索引（WIP） | **SEQ** |
| **KPI 预聚合** | 内建 DataMap，自动路由 | Spark 预聚合写回 + StarRocks 物化视图（需自建） | 接近（实现方式不同） |
| **实时补充** | GaussDB（成熟企业级实时库，独立组件） | StarRocks 查询为主，实时按需（内表弱化，不设大规模实时仓） | **SEQ**（实时仓更成熟） |
| **计算编程模型** | Spark + Hetu SQL（湖内） | Spark（加工）+ StarRocks SQL（查询） | 接近（均 Spark 加工） |
| **资源复用/隔离** | 湖内统一 + 资源管控 | 湖仓统一 + 资源组隔离 | 接近（均优于现状） |
| **开放性/锁定** | 私有格式 + 华为生态绑定 | 开放标准 + 多引擎可读 | **目标** |
| **生态/演进速度** | CarbonData 社区弱化 | Iceberg/StarRocks 社区活跃、迭代快 | **目标** |
| **运维/人才** | 依赖华为体系 | 开源技能市场广 | **目标** |

### 6.2 目标架构相对 SEQ 的优势

1. **不锁定、开放标准**：Iceberg 被 Spark/Flink/Trino/StarRocks/Snowflake 等广泛支持，数据可被多引擎共享，规避私有格式（CarbonData）锁定与社区弱化风险。
2. **多维 + 高并发查询更强**：StarRocks C++ 全向量化 + Data Cache + 物化视图重写，在统计数据的交互式多维分析上普遍优于 HetuEngine（JVM）。
3. **用 Spark on Iceberg 替代 MPP 存储过程**：统计加工从"MPP 黑盒存储过程"变为"声明式、可版本化、可测试的 Spark 作业"，**直接解决现状最痛的耦合问题**（注：此优势主要相对**现状 MPP**；与 SEQ 同样使用 Spark 加工，计算模型相当）。
4. **湖仓真正统一**：详单与统计共用一份 Iceberg 存储 + Spark/StarRocks 共享算力，**资源弹性复用**，根治"两套存储 + 两套算力"的割裂。
5. **演进速度快**：查询加速能力沉在 StarRocks 引擎，随版本（Data Cache/MV/CBO/索引）持续增强，不受单一私有格式社区进度制约。

### 6.3 目标架构相对 SEQ 的劣势/风险

1. **详单点查能力需自建，且因内表弱化而更难**：SEQ 靠 CarbonData 二级索引"白嫖"点查能力，目标架构必须工程化补齐；而本架构**主动弱化 StarRocks 内表**，无法以内表索引为主力兜底，点查更依赖"Spark 排序+Bloom+Data Cache+外置 KV 索引"，这是**最大劣势与风险**。
2. **无原生时空索引**：若有网络覆盖/网格/`IN_POLYGON` 类时空分析，CarbonData 仍独占优势；Iceberg 地理空间能力 2026 初未 GA，需用分区/聚簇近似或外部方案。
3. **预聚合需自行设计维护**：CarbonData 的 Timeseries DataMap 是格式内建、查询自动路由；目标架构需用 Spark 预聚合写回 + StarRocks 物化视图自建（Append-only 下增量刷新友好，是缓解点）。
4. **迁移工程量大**：自研格式 → Iceberg 的数据回灌、HBase 索引语义重建、MPP 存储过程 → Spark 改写，均非小工程。
5. **实时仓能力相对弱**：SEQ 有 GaussDB 作为成熟企业级实时库；目标架构因内表弱化，不设大规模实时仓，真正强实时点查场景需谨慎设计（按需小规模主键表或保留轻量实时层）。

> 客观结论：**在多维统计、开放性、计算解耦、资源复用上目标架构胜出；在详单点查与时空分析这两个 CarbonData "内建索引"强项上 SEQ 占优**。迁移的核心攻坚点正是把后者补齐到"可接受"水平。

## 七、下一步演进策略

> **策略按实战修订**：原"先统计后详单"的理论次序，在实践中因**多维 XDR 查询是市场刚需**而调整为**详单先行**——详单已迁至 Iceberg + StarRocks 且性能基本达标。因此下面以"详单已完成"为前提，把重心放到**当前真正的攻坚：统计数据迁移**。

### 7.1 演进总原则

1. **承认实战次序：详单已先行、统计为当前主战场**：详单迁移已落地达标，无需再"先易后难"地纠结次序；资源与精力应聚焦统计数据迁移这一**数据量与作业量都极大**的硬仗。
2. **统计迁移按"作业 + 数据"双主线推进**：既要把**大量 MPP 存储过程**工程化改写为 Spark 作业（作业主线），也要把**海量存量统计数据**高效回灌入 Iceberg（数据主线），两条线并行但解耦。
3. **可行性先于全量迁移**：每批次先 PoC + 基线对比（与现状 MPP 同口径压测、结果对账），用数据决策，再扩面。
4. **新老并行、灰度切换、可回退**：迁移期双跑/双查对账，保留回退能力，杜绝"一刀切"。
5. **复用详单迁移经验与抽象层**：详单已沉淀的 Spark 写入/Compaction/StarRocks 查询/资源组等经验直接复用；上层应用不直接耦合具体格式/引擎 API，为未来演进预留弹性。

### 7.2 分阶段路线图

#### 阶段 0（已完成）：详单先行迁移

- **驱动力**：多维 XDR 查询是市场刚需，详单分析价值最高、最先承压。
- **成果**：详单已从自研格式迁入 **Iceberg + Parquet/ORC**，由 **StarRocks** 外表直读，**多维查询性能基本达标**；高基数随机点查通过 Spark 排序聚簇 + Bloom + Data Cache（+ 必要时外置索引兜底）处理。
- **沉淀**：形成 Spark 入湖/排序写入、StarRocks 外表查询 + Data Cache、资源组隔离等可复用工程经验，作为统计迁移的基础。

#### 阶段 1（当前重点）：统计数据迁移——数据量 + 作业量双大

> 这是当前真正的攻坚阶段。统计数据的难点不在"查询"（StarRocks 多维已验证可行），而在 **① 海量存量数据回灌、② 大量 MPP 存储过程改写**两件重活。

**① 加工作业主线：大量 MPP 存储过程 → Spark 作业**

- **盘点与分级**：梳理全部存储过程的**血缘/依赖链**，按业务优先级、复杂度、依赖关系分批；识别可下线的冗余作业。
- **分类改写**：纯 SQL 汇聚类可**半自动转写**为 Spark SQL；过程式/游标/复杂控制流类需人工重构为 Spark 作业。
- **统一编排**：用调度框架（如 DolphinScheduler/Airflow）编排 Spark 作业 DAG，替代 MPP 内部调度，显式管理依赖与重跑。
- **等价性对账**：每个作业新老双跑、结果逐字段/逐指标对账，达标后切换、保留回退。

**② 数据主线：海量存量统计数据回灌 + 增量双写**

- 用 **Spark** 批量将存量统计数据回灌入 Iceberg，按时间/区域分区、合理控制文件大小与并发，避免小文件与写放大。
- 迁移期**增量双写**（MPP 与 Iceberg 并行产出），保证切换前数据连续一致。

**③ 查询与加速（复用详单经验）**

- StarRocks 外表承接统计多维/高并发查询；高频固定汇聚用 **StarRocks 物化视图**做查询加速；**资源组**隔离加工与查询负载。

- **预期收益**：**Spark 接管加工**解除"存储过程耦合"、**StarRocks 统一查询 + 资源组**解除"资源隔离"，湖仓资源真正复用。

#### 阶段 2：统一湖仓与下线

- 详单与统计统一在 **Iceberg + Spark + StarRocks** 之上；逐步**下线独立 MPP 集群与自研格式/查询组件**。
- 实时场景按需评估（小规模 StarRocks 主键表或保留轻量实时层），不建大规模实时仓。
- 用 **Spark** 建立小文件 Compaction、快照过期、manifest 重写等**湖仓运维自动化**；维护 StarRocks 物化视图刷新。
- 持续跟踪 Iceberg 二级索引/地理空间能力 GA，适时替换过渡性外置索引。

| 阶段 | 状态 | 目标 | 主要风险 | 退出条件 |
|------|------|------|---------|---------|
| 0 | **已完成** | 详单先行迁移 | 多维查询/点查不达标 | 详单多维查询基本达标 ✓ |
| 1 | **当前重点** | 统计迁移（数据量+作业量双大） | 存储过程改写量大、对账复杂、回灌耗时 | 作业改写对账通过 + 数据回灌完成 + 多维/并发达标 |
| 2 | 后续 | 统一下线 | 实时/运维短板 | MPP + 自研格式安全下线 |

### 7.3 关键技术难点与对策

> 按当前阶段（统计迁移）重排难点优先级：作业量与数据量相关难点上升为最高，详单点查降为"已基本解决/剩余兜底"。

| 难点 | 风险 | 对策 |
|------|------|------|
| **大量 MPP 存储过程改写（当前最大工程量）** | 最高 | 血缘梳理 + 分批分级；SQL 类半自动转写 Spark SQL、过程式人工重构；统一调度编排 DAG；逐作业等价性对账 |
| **海量统计数据回灌 / 增量双写** | 高 | Spark 批量回灌 + 分区分批 + 文件大小/并发控制；迁移期 MPP↔Iceberg 增量双写保连续一致 |
| **统计多维并发 SLA** | 中 | StarRocks 物化视图预聚合 + 资源组隔离 + 缓存预热（CACHE SELECT） |
| **加工时效（原 MPP 近实时 vs Spark 批）** | 中 | 关键链路用微批/更短调度周期；必要时 StarRocks 端补充近实时汇聚 |
| **海量小文件/写放大** | 中 | Spark 定期 Compaction + 合理分区粒度 + 批量提交 |
| **详单冷数据随机点查（剩余子风险）** | 中 | 多维查询已达标；冷随机点查用外置 KV/HBase 二级索引兜底，避免大范围扫描 |
| **迁移期一致性** | 中 | 双写双查对账 + 灰度 + 可回退 |

### 7.4 风险登记与回退预案

- **R1 存储过程改写工作量/对账风险（当前首要）**：作业体量大、逻辑复杂；以分批改写 + 自动转写 + 逐作业对账控制风险，未达标的作业暂留 MPP 承接，不强迁。
- **R2 数据回灌耗时/资源冲突**：海量回灌与在线加工抢资源；错峰回灌、限流并发、分区分批，必要时临时扩 Spark 资源。
- **R3 加工时效回退**：若 Spark 批时效不及原 MPP，关键指标链路改微批/缩短周期或 StarRocks 端补充近实时汇聚。
- **R4 详单冷数据点查个案**：对少数纯随机高基数冷点查，用外置 KV 索引兜底；多维查询已达标，不影响主体。
- **R5 资源/成本超预期**：分离存算（StarRocks Shared-Data）+ 对象存储控成本；按热度分层缓存。

## 八、结论与建议

1. **方向正确且与 SEQ 同构**：把存储与计算重心搬回湖中——**Iceberg 存、Spark 算、StarRocks 查**，用开放栈替代自研格式/查询与独立 MPP，本质是"做一个开放栈版本的 SEQ（CarbonData+Spark+Hetu）"，符合行业趋势，且在**开放性、多维查询、计算解耦、资源复用**上优于现状与 SEQ。
2. **详单已先行迁移、多维查询基本达标**：受市场刚需驱动，详单先行迁入 Iceberg + StarRocks，多维 XDR 查询性能已基本达标（剩余仅"冷数据纯随机高基数点查"需外置索引兜底）。这验证了开放栈在电信运维核心分析场景的可行性，原"详单为最大风险"的判断在多维维度上已被实战证伪。
3. **当前真正的硬仗是统计数据迁移（量大 + 作业多）**：统计数据的难点不在查询，而在 **① 海量存量数据回灌、② 大量 MPP 存储过程向 Spark 作业的工程化改写**。应按"作业主线（盘点分级 + 半自动转写 + 统一编排 + 逐作业对账）+ 数据主线（Spark 批量回灌 + 增量双写）"双线推进，全程灰度 + 可回退；迁完即解除"资源隔离 + 存储过程绑定"两大现状痛点。
4. **客观看待与 SEQ 的差距**：在详单点查、时空分析、实时仓成熟度上短期不及 SEQ（CarbonData 内建索引 + GaussDB），需接受"用工程化补齐 + 内表弱化换开放与解耦"的权衡；但中长期随 StarRocks 引擎演进与 Iceberg 索引 GA，差距将收窄，而开放栈的生态与人才优势会持续放大。
