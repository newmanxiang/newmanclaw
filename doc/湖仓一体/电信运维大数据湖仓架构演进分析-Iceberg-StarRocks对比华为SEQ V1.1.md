## 一、问题陈述与核心结论

### 1.1 问题背景

电信运维大数据的两类核心数据：

- **XDR 详单**：会话级明细记录（S1-U/Gn/信令/话单等），单表数十亿~万亿行，日增 TB 级，典型查询是**按 IMSI/MSISDN/会话 ID 等高基数键的点查/明细回溯**，以及**多维过滤分析**。
- **XDR 统计数据**：由详单加工的多粒度汇聚指标（时间 × 区域 × 小区 × 网元 × KPI），数据量同样巨大，查询方式**多样、多维、并发要求高**（运维监控、KPI 报表、即席下钻）。

**我司现状**（架构定型于 2020 年前 Hadoop 生态早期）：

- 详单：**HBase 存索引 + 自研 HDFS 文件存储格式**，查询用**自研查询组件**（针对详单点查定制，**不支持多维查询**）。
- 统计：为满足多维 + 高并发，只能建设**规模巨大的 MPP 数据库集群**。

**两个突出副作用**：

1. **湖仓资源隔离、难以复用**：详单在 Hadoop 湖、统计在 MPP 仓，两套存储 + 两套算力，资源无法弹性互通。
2. **计算被 MPP 绑死**：统计数据之上的加工计算只能写在 **MPP 数据库的存储过程**里，逻辑与引擎强耦合、难维护、难迁移。

**华为对标产品 SEQ**：采用 **CarbonData + Spark + HetuEngine** 作为湖，**GaussDB 作为实时数据库补充**，存储、计算、查询均在湖内完成——"湖内存算一体"。

**我司目标**：切换到 **Iceberg + Spark + StarRocks**——**Spark** 作湖内计算引擎（承接现状 MPP 存储过程的统计加工）、**StarRocks** 主要作查询引擎（外表直读 Iceberg、**内表弱化**）。该目标栈与 SEQ（CarbonData + Spark + HetuEngine + GaussDB）**结构同构**（"湖格式 + Spark + 查询引擎"），差异收敛为：① 存储格式（开放 Iceberg vs 私有 CarbonData）；② 查询引擎（StarRocks C++ 向量化 vs HetuEngine JVM）；③ 以 StarRocks 兼顾查询、弱化独立实时仓。

### 1.2 核心结论（先给答案）

| 问题 | 结论 |
|------|------|
| **第一性原理（本文主线）** | 一切 OLAP 性能可还原为两个因子：**读得少（Data Skipping）× 算得快（向量化并行执行）**。所有特性（索引/字典/缓存/向量化/物化视图……）本质都在做这两件事之一，背后是三条系统兑换原理：**空间换时间、预计算换时间、局部性/减少数据移动**（详见第四章）。 |
| **两条路线的关系** | **不是"把智能放数据还是放引擎"的二选一**，而是**有侧重、可借鉴、可组合**：CarbonData 把"读得少"机制**做成格式内建、自动**（细粒度/二级/时空索引、预聚合）；Iceberg+StarRocks 把"读得少"做成**开放可工程化调优的原语**（分区/排序聚簇/Bloom/分桶/Z-order），把"算得快"**做到极致**（C++ 向量化/Data Cache/MV）。我司详单攻关正是在 Iceberg 数据层做足了优化（合理分桶数、Bloom、Saturn 入库排序）。 |
| **场景适配** | 电信运维主流负载是**多维聚合（"算得快"主场）→ Iceberg+StarRocks 强适配**；**详单高基数点查（"读得少"主场）** 需在数据层把"读得少"工程化补回来——**实战中详单多维查询已基本达标**，剩余仅"冷数据纯随机点查"用外置索引兜底。 |
| **演进策略（按实战修订）** | **详单已先行迁移、统计为当前攻坚**：① 详单（多维查询市场刚需）已迁至 Iceberg + StarRocks，性能基本达标；② **当前重点是统计数据迁移**，难在**数据量与加工作业量都极大**（大量 MPP 存储过程改写为 Spark 作业 + 海量回灌）；③ 最后统一下线 MPP 与自研残余。 |

**一句话**：把任何查询拆成 **"读得少 × 算得快"**——多维聚合靠"算得快"（StarRocks 主场），详单点查靠"读得少"（需数据层工程化补齐）；**两条路线只是侧重不同、可互相借鉴**，目标架构在电信主流负载上完全适配，详单点查已用数据层优化基本达标，下一步真正的硬仗是**数据量与作业量都极大的统计数据迁移**。

## 二、三种架构画像

### 2.1 华为 SEQ：CarbonData + Spark + HetuEngine + GaussDB

```
            ┌──────────────────────────────────────┐
            │        分析 / 运维 / KPI 应用          │
            └───────────────┬──────────────────────┘
        ┌───────────────────┼───────────────────────┐
        │                                            │
┌───────▼────────┐                         ┌─────────▼─────────┐
│  HetuEngine    │   查询/联邦/下推         │   GaussDB(实时仓)  │
│ (交互式查询)   │                         │  实时数据库补充    │
└───────┬────────┘                         └─────────┬─────────┘
        │                                            │
┌───────▼────────┐   批处理/入湖/加工        ┌────────▼─────────┐
│     Spark      │◄────────────────────────►│  实时写入/点查    │
└───────┬────────┘                          └──────────────────┘
        │
┌───────▼────────────────────────────────────────────────────┐
│           CarbonData（湖内存储格式，自带索引）               │
│  多级索引 + 全局字典 + Sort/二级/时空索引 + 预聚合 DataMap   │
└───────┬─────────────────────────────────────────────────────┘
        │
┌───────▼────────────────────────────────────────────────────┐
│                HDFS / OBS（对象/分布式存储）                 │
└─────────────────────────────────────────────────────────────┘
```

- **存算重心在湖内**：CarbonData 把索引/预聚合内建进格式，Spark 负责批量加工与入湖，HetuEngine 负责交互式与联邦查询。
- **GaussDB 仅作实时补充**：承接实时点查/低延迟场景。
- **本质**：**私有重型存储格式 + 湖内闭环**，加速能力大多"沉在格式里"。

### 2.2 我司现状：HBase 索引 + 自研 HDFS 格式 + 自研查询 + 大规模 MPP

```
   ┌─────────────────────┐         ┌──────────────────────────┐
   │   详单查询应用       │         │   统计/多维/报表应用      │
   │  (按用户/会话点查)   │         │  (多维 + 高并发)          │
   └─────────┬───────────┘         └─────────────┬────────────┘
             │                                    │
   ┌─────────▼───────────┐         ┌─────────────▼────────────┐
   │   自研查询组件       │         │     大规模 MPP 集群       │
   │ (详单定制,不支持多维)│         │  存储+计算+存储过程加工   │
   └─────────┬───────────┘         └─────────────┬────────────┘
             │                                    │ (独立存储,独立算力)
   ┌─────────▼───────────────────────────┐       │
   │  HBase 索引  +  自研 HDFS 文件格式   │       │
   └─────────┬───────────────────────────┘       │
             │                                    │
   ┌─────────▼────────────────────────────────────▼──────────┐
   │            两套独立体系，资源隔离、难以复用              │
   └──────────────────────────────────────────────────────────┘
```

- **详单侧**：HBase 维护点查索引，明细落自研 HDFS 文件；自研查询组件专为"按 key 取明细"定制——**点查高效，但不支持多维分析**。
- **统计侧**：为满足多维 + 高并发，独立建设大规模 MPP；统计加工写在 MPP **存储过程**中。
- **副作用根因**：详单（湖）与统计（仓）是**两套存储 + 两套算力**，无法弹性复用；加工与 MPP 引擎强绑定。

### 2.3 目标架构：Iceberg + Spark + StarRocks（湖内存算）

```
       ┌────────────────────────────┐   ┌──────────────────────────────┐
       │   ETL / 统计加工 / 回灌     │   │  详单点查 + 多维统计 + 即席下钻│
       └──────────────┬─────────────┘   └───────────────┬──────────────┘
                      │ 批计算/写回                       │ 标准 SQL(交互式)
       ┌──────────────▼─────────────┐   ┌───────────────▼──────────────┐
       │    Spark（湖内计算引擎）    │   │   StarRocks（查询引擎,C++向量化)│
       │  ETL/聚合/排序写入/Compact │   │  外表直读 Iceberg + Data Cache │
       │  替代 MPP 存储过程的加工    │   │  + 物化视图重写 + 资源组隔离   │
       │                            │   │  内表(主键/索引)：弱化、按需   │
       └──────────────┬─────────────┘   └───────────────┬──────────────┘
                      │ 读写                External Catalog│ (外表,零搬运)
       ┌──────────────▼───────────────────────────────────▼──────────────┐
       │                Iceberg（开放表格式 / 统一表层）                   │
       │   metadata/manifest 裁剪 + 隐藏分区 + 排序聚簇 + Bloom/Puffin     │
       │   数据文件: Parquet/ORC                                          │
       └──────────────────────────────┬──────────────────────────────────┘
                                      │
       ┌──────────────────────────────▼──────────────────────────────────┐
       │                  HDFS / S3 / OSS（统一对象存储）                  │
       └───────────────────────────────────────────────────────────────────┘
```

- **职责清晰**：**Spark 算**（ETL、统计加工、排序聚簇写入、Compaction）、**StarRocks 查**（外表直读 Iceberg）、**Iceberg 存**；详单与统计共享同一存储与算力池。
- **StarRocks 内表弱化**：主用作查询引擎，**不把数据沉淀进内表作为主存**；内表仅在极热小窗口按需、最小化使用。
- **本质**：**开放轻量表格式 + Spark 计算 + 强向量化查询引擎 + 统一湖仓**——与 SEQ **结构同构**，但用开放格式 + StarRocks 替代私有格式 + HetuEngine。

## 三、现状架构的根因剖析与副作用

### 3.1 为什么会形成现状（历史合理性）

| 现状选择 | 当年（2020 前）原因 | 当时的合理性 |
|---------|-------------------|------------|
| HBase 存索引 | 早期 Hadoop 缺少成熟列存表格式（Iceberg 2017 起步、当时未成熟），HBase 是最现实的高基数点查方案 | 合理 |
| 自研 HDFS 文件格式 | Parquet/ORC 当时对电信明细的压缩/裁剪不够理想，CarbonData 属华为私有 | 合理（但埋下锁定隐患） |
| 自研查询组件（仅点查） | 业务首要诉求是详单回溯，多维分析需求尚未爆发 | 合理（但欠缺扩展性） |
| 独立大规模 MPP | 当时湖上引擎（Hive/早期 Presto）无法满足统计的多维 + 高并发 + 低延迟 | 合理（但造成湖仓割裂） |

**关键判断**：现状不是"设计失误"，而是**时代局限下的合理选择**。但随着开放表格式（Iceberg）与向量化湖上引擎（StarRocks）成熟，这些选择的**技术债已显性化**。

### 3.2 现状的核心副作用（迁移要解决的目标）

| 副作用 | 表现 | 业务/工程代价 |
|--------|------|--------------|
| **湖仓割裂、资源不可复用** | 详单（HDFS+HBase）与统计（MPP）两套存储 + 两套算力 | 资源利用率低、扩容各自为政、成本高 |
| **计算与 MPP 强耦合** | 统计加工只能写 MPP 存储过程 | 逻辑黑盒、难测试、难迁移、人才依赖 |
| **详单不支持多维** | 自研查询组件仅按 key 取明细 | 多维分析需把数据再倒进 MPP，链路冗长、时效差 |
| **自研格式/组件维护成本** | 私有格式与查询组件需自行长期维护 | 团队负担重、生态隔离、招聘困难 |
| **数据多副本** | 同源数据在 HDFS、HBase、MPP 多处存储 | 存储浪费、一致性风险 |

## 四、第一性原理与技术路线分析

> 本章是全文的理论核心，分三步：**4.1** 把性能问题拆到第一性原理（两个因子 + 业界机制 + 底层兑换原理）；**4.2** 客观分析两条路线**各自的机制与侧重**（非二选一）；**4.3** 落到电信运维，讲清 Iceberg + StarRocks 的**优势、差距与弥补**（含"多维聚合用 Spark 还是 StarRocks""全程外表何时用物化视图"两个高频实操问题）。

### 4.1 第一性原理：查询性能的本质与可促成的机制

任何分析型查询的耗时，剥到最底层，都可写成：

```
查询耗时 ≈  需要处理的数据量  ÷  处理数据的速度
          └──── 读得少 ────┘   └──── 算得快 ────┘
```

但"读得少、算得快"只是结论，**关键是"怎么才能做到"**。下面把两个因子各自拆到业界成熟机制，并点明每种机制背后的"兑换"代价。

#### 因子一：读得少 —— 业界统称 Data Skipping（数据跳过 / 裁剪）

要在海量数据里少读，唯一办法是**在真正读数据之前，就判定"哪些数据必然不含结果"从而跳过**。这必须依赖预先维护的"元信息 / 辅助结构"。按粒度与实现，业界成熟机制如下：

| 机制 | 业界专业概念 | 原理（怎么帮你少读） | 底层兑换 |
|------|------------|--------------------|---------|
| 分区裁剪 | **Partition Pruning** | 按列值物理分目录，谓词命中即整目录跳过 | 组织换时间 |
| 区间统计 | **Zone Map / Min-Max / Column Statistics** | 每个数据块存 min/max，谓词不在区间则跳过该块 | 空间换时间 |
| 布隆过滤 | **Bloom Filter** | 概率性判定"某值是否可能存在"，判否即跳过 | 空间换时间 |
| 二级/倒排/位图索引 | **Secondary / Inverted / Bitmap Index** | 维护"值 → 物理位置"映射，高基数点查直接定位 | 空间换时间 |
| 数据聚簇/排序 | **Data Clustering / Sort Order / Z-order / Hilbert（空间填充曲线）** | 把"常一起被查"的数据在物理上排到一起，让 min/max 与分桶裁剪更有效 | 写时计算换读时 |
| 列裁剪 | **Projection / Column Pruning** | 列存只读用到的列，跳过无关列 | 列存天然 |
| 预聚合 / 物化视图 | **Materialized View / Pre-aggregation / OLAP Cube** | 预先把结果算好，查询直接读结果而非扫明细 | 预计算换时间 |

> 你的直觉"索引是空间换时间、统计信息是预先计算换时间"**完全正确**——它正对应上表的"空间换时间"与"预计算换时间"两类。

#### 因子二：算得快 —— 业界统称 Vectorized / Parallel Execution（向量化并行执行）

对真正读进来的数据，要尽快算完，业界机制如下：

| 机制 | 业界专业概念 | 原理（怎么帮你算快） |
|------|------------|--------------------|
| 向量化执行 | **Vectorized Execution** | 按列"一次一批"处理，摊薄逐行的解释/函数调用开销 |
| 单指令多数据 | **SIMD** | 一条 CPU 指令处理多个数据，数据级并行 |
| 代码生成 | **Codegen / JIT / Whole-stage Codegen** | 把算子编译为机器码，消除解释执行开销 |
| 大规模并行 | **MPP / Parallelism / Pipelining** | 多节点多核并行 + 流水线，吞吐线性扩展 |
| 编码上计算 | **Encoded Execution（字典编码 + 延迟物化）** | 直接在压缩/编码数据上聚合比较，减少 CPU 与内存带宽 |
| 缓存与本地性 | **Caching / Data Locality** | 把热数据搬到离计算最近处（内存/NVMe），利用局部性 |
| 计算下推 | **Predicate/Aggregation Pushdown / Compute-Near-Data** | 把过滤聚合推到离数据近处，减少数据搬运 |
| 代价优化 | **Cost-Based Optimization（CBO）** | 用统计选更优计划（join 顺序/分布），同时减少读与算 |

#### 一切的根：三条系统级"兑换"原理

把上面十几种机制再抽象一层，背后只有三条计算机系统的根本权衡——**没有银弹，全是兑换**：

1. **空间换时间（Space–Time Tradeoff）**：索引、Bloom、Zone Map、缓存、物化视图——用额外存储换查询时少读/少算。
2. **预计算 / 写时换读时（Precomputation / Shift to Write-time）**：物化视图、预聚合、写时排序聚簇、写时建索引——把工作从"查询时"挪到"写入时"。
3. **局部性与减少数据移动（Locality / Minimize Data Movement）**：缓存、分桶 colocation、计算下推、列裁剪——让数据离计算更近、搬得更少。
4. （反向参照）**时间换空间（压缩）**：压缩省存储/IO，但增加解压 CPU——提醒"兑换是双向的，要按场景权衡"。

> **本质洞察**：每多一份索引/缓存/物化，就多一份存储与维护成本；每多一分写时排序，就多一分入库延迟。**架构选型的本质，是"为哪类查询、付出哪种兑换成本"。** 这正是理解两条技术路线的钥匙。

### 4.2 两种技术路线的机制选择与侧重

**先纠正一个过于简单的说法**：两条路线不是"把智能放数据 vs 放引擎"的二选一。事实是——**两条路线都同时使用"读得少（数据层）"与"算得快（引擎层）"机制**。我司在详单性能攻关中，正是在 **Iceberg 数据层**做了大量"读得少"优化（合理**分桶数**、**Bloom 索引列**、**Saturn 实时入库时的排序聚簇**等），效果显著。所以真正的区别是**两点**：

- **A. 侧重不同**：每条路线把哪一类机制做得更强、作为主要抓手。
- **B. 内建程度不同**：机制是"格式自动内建、开箱即用"，还是"以开放原语提供、需工程化调优"。

| 机制（对应 4.1） | CarbonData + HetuEngine（SEQ 路线） | Iceberg + StarRocks（目标路线） |
|------------------|----------------------------------|------------------------------|
| 分区裁剪 | ✅ | ✅ 隐藏分区 + 分区演进 |
| Zone Map / min-max | ✅ **多级（Blocklet/Page，细）** | ✅ 文件/RowGroup 级（较粗） |
| Bloom Filter | ✅ | ✅ Parquet/ORC 按列可配（**我司详单已用**） |
| 二级/倒排索引 | ✅ **格式内建** | ⚠️ 无格式级内建（靠外置索引或引擎侧补） |
| 数据聚簇/排序/Z-order | ✅ Sort Columns | ✅ 写时排序/分桶/Z-order（**我司 Saturn 入库排序、分桶调优**） |
| 时空索引 | ✅ GeoHash/GeoSOT | ⚠️ 无原生（聚簇近似/外部方案） |
| 预聚合/物化视图 | ✅ DataMap **自动路由（格式内建）** | ✅ StarRocks 异步 MV + 透明改写（**引擎侧**） |
| 向量化 / SIMD / Codegen | ⚠️ HetuEngine（JVM，有限） | ✅ StarRocks **C++ 全向量化（强）** |
| 缓存 / 本地性 | ⚠️ 弱 | ✅ **Data Cache（内存 + NVMe）** |
| CBO | 一般 | ✅ manifest + Puffin 统计 |
| 开放性 / 可组合 | 私有、自动但封闭 | 开放、可工程化组合 |

**正确的读法（呼应 4.1）**：

- **CarbonData 的侧重** = 把"读得少"的机制（尤其细粒度索引、二级索引、时空索引、预聚合）**做成格式内建、自动**——开箱即用、随数据走，但**私有、重、演进慢**。
- **Iceberg + StarRocks 的侧重** = 存储层提供**开放、可组合的"读得少"原语**（分区/排序聚簇/Bloom/Z-order/分桶），由工程**按场景调优**；引擎层把"算得快"（向量化/缓存/MV/CBO）**做到极致**。
- **二者可借鉴、可组合**：为满足详单点查这类特定场景，Iceberg 路线完全可以——也应该——在数据层做足"读得少"优化（**这正是我司的实战**）；反之 CarbonData 也依赖引擎执行。

> **修正后的核心一句**：**两条路线都在"读得少 × 算得快"上下功夫；区别在于 CarbonData 把"读得少"尽量做成格式内建、自动，而 Iceberg + StarRocks 把"读得少"做成开放可调优、把"算得快"做到极致。是侧重与内建程度之别，不是有无之别；为特定场景达标，双方都会互相借鉴。**

### 4.3 电信运维场景下 Iceberg + StarRocks 的适配性：优势、差距与弥补

把 4.1 的"读得少 / 算得快"和 4.2 的"侧重"套到电信运维的实际负载上，结论清晰。

#### 4.3.1 负载适配总览

| 电信典型负载 | 本质（看可裁剪性） | Iceberg+StarRocks 适配 | 差距与弥补手段 |
|------------|------------------|----------------------|---------------|
| **多维聚合**（time×region×小区×KPI） | **算得快**为主（大范围扫描聚合，可裁剪有限） | ✅ **强**（C++ 向量化 + Data Cache + MV + CBO） | 无明显差距，主场 |
| **详单高基数点查**（按 IMSI/会话 ID） | **读得少**为主（选择性极高、万里挑一） | ⚠️ 需补（无格式级二级索引） | 数据层"读得少"工程化：排序/分桶聚簇 + Bloom + Data Cache；冷随机点查用外置 KV 索引兜底 |
| **时空范围查询**（覆盖/网格/`IN_POLYGON`） | **读得少**（空间局部性） | ⚠️ 弱（无原生时空索引） | GeoHash 列 + 排序聚簇近似，或外部时空方案；关注 Iceberg Geospatial GA |
| **海量统计加工 / ETL** | **写时计算**（预计算换时间） | ✅ **Spark** 批处理 | 主场 |
| **高并发即席查询** | **算得快 + 缓存** | ✅ **强**（向量化 + Data Cache + 资源组隔离） | 主场 |

> 关键判断口诀：**先问"这条查询能裁掉多少数据"**——能裁掉绝大部分（高选择性）→ 拼"读得少"（详单点查/时空，需数据层补齐）；裁不掉多少（大范围聚合）→ 拼"算得快"（多维聚合，StarRocks 主场）。

#### 4.3.2 优势：为什么 Iceberg + StarRocks 适配电信运维主流

电信运维分析的**主流负载是多维聚合与高并发即席**，恰是"算得快"主场：

1. **多维/高并发查询强**：StarRocks C++ 全向量化 + SIMD + Data Cache + CBO，交互式延迟与并发能力突出，远胜 JVM 系引擎。
2. **加工与查询解耦**：Spark 承接重型统计加工（去 MPP 存储过程），StarRocks 专注查询，职责清晰、各取所长。
3. **湖仓统一、资源复用**：详单与统计共用一份 Iceberg + 共享 Spark/StarRocks 算力 + 资源组隔离，根治"两套存储两套算力"。
4. **开放不锁定**：Iceberg 被多引擎广泛支持，规避私有格式与社区弱化风险，人才/生态友好。

#### 4.3.3 差距与弥补：详单点查与时空查询

这两类是"读得少"主场，开放栈默认把细粒度"读得少"做薄，需在**数据层把"读得少"工程化补回来**（即 4.2 的"借鉴"，也是我司实战）：

- **详单高基数点查**：
  - 写时按点查键**排序/分桶聚簇**（Saturn 实时入库排序、合理分桶数）→ 让 min/max 与分桶裁剪生效；
  - 对点查列建 **Bloom Filter** → 文件级快速排除；
  - **StarRocks Data Cache** → 重复访问本地化；
  - 冷数据纯随机点查 → 保留/新建**外置 KV/二级索引（如 HBase）** 做"键 → 文件/分区"定位兜底；
  - 中长期 → 跟踪 **Iceberg 二级索引** 演进。
  - **实战印证**：经上述数据层攻关，**详单多维查询性能已基本达标**，剩余仅冷随机点查需外置索引兜底。
- **时空范围查询**：无原生时空索引，用 **GeoHash 列 + 排序聚簇**近似空间局部性，或接外部时空引擎；关注 Iceberg Geospatial GA。

#### 4.3.4 高频实操问题一：多维聚合切换时，用 Spark 还是 StarRocks？

**结论：看是"在线查询"还是"离线加工"——两者分工，不是二选一。**

| 多维聚合的形态 | 用谁 | 为什么 |
|--------------|------|-------|
| **在线/交互式多维聚合查询**（用户发起、要秒级响应、要并发） | **StarRocks** | 这是"算得快"典型负载；StarRocks C++ 全向量化 + Data Cache + CBO 专为低延迟高并发交互式查询设计。Spark 的任务调度/启动开销大，不适合交互式。 |
| **离线/批量的多维预聚合加工**（定时把明细汇聚成统计表/指标层，即原 MPP 存储过程那部分） | **Spark** | 这是"写时计算（预计算换时间）"的重型 ETL，吞吐优先、容错好、适合海量批处理；产物（汇聚表）写回 Iceberg，再交给 StarRocks 查询。 |

> 一句话：**Spark 负责"把多维聚合提前算好"（离线加工），StarRocks 负责"对外提供多维聚合查询"（在线服务）**。这正是 4.1 中"预计算换时间（Spark 写时算）"与"算得快（StarRocks 查时算）"的落地分工。

#### 4.3.5 高频实操问题二：全程用外表，什么时候才用物化视图？

**结论：当"某类重型多维聚合被高频重复查询、且外表直查 + Data Cache 仍不达标"时，才为它建物化视图。**

- 全程外表（StarRocks External Catalog 直读 Iceberg）是**默认与主力**；物化视图**不是把数据搬进内表当主存**，而是把"某一类高频、固定模式的重型聚合查询的结果**预计算并固化**"（即 4.1 的"预计算换时间"）。
- **触发使用 MV 的判断**：某类多维聚合（核心看板/固定报表）**反复被查、计算重、且外表直查 + Data Cache 仍无法稳定满足 SLA** → 为它建**异步物化视图**；StarRocks 通过**透明查询重写**自动把命中查询改写到 MV，**业务 SQL 零改造**；Append-only 数据下 MV **分区级增量刷新**很友好。
- **与"内表弱化"不冲突**：MV 存的是**小体量派生聚合结果**（不是详单/明细主数据），属于查询加速层而非主存储；明细仍在 Iceberg 外表。
- **不需要 MV 的情况**：低频、临时、模式多变的即席查询——直接外表 + Data Cache 即可，建 MV 反增维护成本（刷新、失效管理）。

## 五、与华为 SEQ 的优劣势对比

> 本章是第四章机制分析在 **SEQ 产品语境**下的应用结论。**结构同构提示**：目标架构（Iceberg + **Spark** + StarRocks）与 SEQ（CarbonData + **Spark** + HetuEngine + GaussDB）形态对称——**批计算都用 Spark**，差异集中在 ① 存储格式、② 查询引擎、③ 目标架构用 StarRocks 兼顾查询、弱化独立实时仓（GaussDB）。

### 5.1 逐维度对比

| 维度 | 华为 SEQ（CarbonData+Spark+Hetu+GaussDB） | 目标架构（Iceberg+Spark+StarRocks） | 占优 |
|------|----------------------------------------|------------------------------|------|
| **存储格式** | 私有 CarbonData，重索引、自带预聚合 | 开放 Iceberg + Parquet/ORC，标准化 | 各有侧重 |
| **批计算引擎** | Spark | Spark | 相同 |
| **详单高基数点查** | CarbonData 二级索引，开箱即用 | 需数据层补齐（排序/分桶+Bloom+外置索引；内表弱化） | **SEQ** |
| **多维统计查询** | HetuEngine（JVM） | StarRocks C++ 全向量化 | **目标** |
| **高并发交互式** | Hetu 中等 | StarRocks 强（向量化+缓存+MV） | **目标** |
| **时空查询** | CarbonData 时空索引（GeoHash/GeoSOT） | 无原生时空索引（聚簇近似/外部方案） | **SEQ** |
| **KPI 预聚合** | 内建 DataMap，自动路由 | Spark 预聚合写回 + StarRocks 物化视图（需自建） | 接近（实现不同） |
| **实时补充** | GaussDB（成熟企业级实时库，独立组件） | StarRocks 查询为主，实时按需（内表弱化） | **SEQ**（实时仓更成熟） |
| **计算编程模型** | Spark + Hetu SQL（湖内） | Spark（加工）+ StarRocks SQL（查询） | 接近（均 Spark 加工） |
| **资源复用/隔离** | 湖内统一 + 资源管控 | 湖仓统一 + 资源组隔离 | 接近（均优于现状） |
| **开放性/锁定** | 私有格式 + 华为生态绑定 | 开放标准 + 多引擎可读 | **目标** |
| **生态/演进速度** | CarbonData 社区弱化 | Iceberg/StarRocks 社区活跃、迭代快 | **目标** |
| **运维/人才** | 依赖华为体系 | 开源技能市场广 | **目标** |

### 5.2 目标架构相对 SEQ 的优势

1. **不锁定、开放标准**：Iceberg 被 Spark/Flink/Trino/StarRocks/Snowflake 等广泛支持，数据可被多引擎共享。
2. **多维 + 高并发查询更强**：StarRocks C++ 全向量化 + Data Cache + 物化视图重写，普遍优于 HetuEngine（JVM）。
3. **用 Spark on Iceberg 替代 MPP 存储过程**：加工从"MPP 黑盒存储过程"变为"声明式、可版本化、可测试的 Spark 作业"（注：此优势主要相对**现状 MPP**；与 SEQ 同样用 Spark 加工，计算模型相当）。
4. **湖仓真正统一**：详单与统计共用一份 Iceberg + 共享 Spark/StarRocks 算力，资源弹性复用。
5. **演进速度快**：查询加速能力沉在 StarRocks 引擎，随版本持续增强，不受单一私有格式社区进度制约。

### 5.3 目标架构相对 SEQ 的劣势/风险

1. **详单点查需数据层工程化补齐，且内表弱化使其更依赖外置索引**：SEQ 靠 CarbonData 二级索引"内建"，目标架构需用"排序/分桶 + Bloom + Data Cache + 外置 KV 索引"补齐（实战已基本达标，剩余冷随机点查靠外置索引）。
2. **无原生时空索引**：时空分析 CarbonData 仍占优；Iceberg 地理空间能力 2026 初未 GA。
3. **预聚合需自行设计维护**：CarbonData DataMap 格式内建、自动路由；目标架构需 Spark 预聚合写回 + StarRocks 物化视图自建。
4. **迁移工程量大**：自研格式 → Iceberg 回灌、HBase 索引语义重建、MPP 存储过程 → Spark 改写。
5. **实时仓能力相对弱**：SEQ 有 GaussDB；目标架构内表弱化，不设大规模实时仓，强实时场景需谨慎设计。

> 客观结论：**在多维统计、开放性、计算解耦、资源复用上目标架构胜出；在详单点查与时空分析这两个 CarbonData "内建索引"强项上 SEQ 占优**。但二者机制可借鉴，目标架构通过数据层工程化优化已把详单查询补齐到基本达标。

## 六、下一步演进策略

> **策略按实战修订**：原"先统计后详单"的理论次序，在实践中因**多维 XDR 查询是市场刚需**而调整为**详单先行**——详单已迁至 Iceberg + StarRocks 且性能基本达标。下面以"详单已完成"为前提，把重心放到**当前真正的攻坚：统计数据迁移**。

### 6.1 演进总原则

1. **承认实战次序：详单已先行、统计为当前主战场**：资源与精力聚焦统计数据迁移这一**数据量与作业量都极大**的硬仗。
2. **统计迁移按"作业 + 数据"双主线推进**：把**大量 MPP 存储过程**工程化改写为 Spark 作业（作业主线）+ 把**海量存量统计数据**高效回灌入 Iceberg（数据主线），并行解耦。
3. **可行性先于全量迁移**：每批次先 PoC + 基线对比（与现状 MPP 同口径压测、结果对账），用数据决策再扩面。
4. **新老并行、灰度切换、可回退**：迁移期双跑/双查对账，保留回退能力。
5. **复用详单迁移经验与抽象层**：详单已沉淀的 Spark 写入/Compaction/StarRocks 查询/资源组经验直接复用；上层应用不直接耦合具体格式/引擎 API。

### 6.2 分阶段路线图

#### 阶段 0（已完成）：详单先行迁移

- **驱动力**：多维 XDR 查询是市场刚需，详单分析价值最高、最先承压。
- **成果**：详单已迁入 **Iceberg + Parquet/ORC**，由 **StarRocks** 外表直读，**多维查询性能基本达标**；高基数点查通过数据层优化（排序/分桶聚簇 + Bloom + Data Cache + 必要时外置索引兜底）处理。
- **沉淀**：形成 Spark 入湖/排序写入、StarRocks 外表查询 + Data Cache、资源组隔离等可复用工程经验。

#### 阶段 1（当前重点）：统计数据迁移——数据量 + 作业量双大

> 难点不在"查询"（StarRocks 多维已验证可行），而在 **① 海量存量数据回灌、② 大量 MPP 存储过程改写**。

**① 加工作业主线：大量 MPP 存储过程 → Spark 作业**

- **盘点与分级**：梳理全部存储过程的**血缘/依赖链**，按优先级、复杂度、依赖分批；识别可下线的冗余作业。
- **分类改写**：纯 SQL 汇聚类**半自动转写** Spark SQL；过程式/游标/复杂控制流类人工重构为 Spark 作业。
- **统一编排**：用调度框架（DolphinScheduler/Airflow）编排 Spark 作业 DAG，替代 MPP 内部调度。
- **等价性对账**：每个作业新老双跑、逐字段/逐指标对账，达标后切换、保留回退。

**② 数据主线：海量存量回灌 + 增量双写**

- 用 **Spark** 批量回灌存量统计数据入 Iceberg，按时间/区域分区、控制文件大小与并发，避免小文件与写放大。
- 迁移期 **MPP ↔ Iceberg 增量双写**，保证切换前数据连续一致。

**③ 查询与加速（复用详单经验）**

- StarRocks 外表承接统计多维/高并发查询；高频固定汇聚用 **StarRocks 物化视图**加速；**资源组**隔离加工与查询负载。
- **预期收益**：Spark 接管加工解除"存储过程耦合"、StarRocks 统一查询 + 资源组解除"资源隔离"。

#### 阶段 2：统一湖仓与下线

- 详单与统计统一在 **Iceberg + Spark + StarRocks**；逐步**下线独立 MPP 集群与自研格式/查询组件**。
- 实时场景按需评估（小规模 StarRocks 主键表或保留轻量实时层），不建大规模实时仓。
- 用 **Spark** 建立 Compaction、快照过期、manifest 重写等湖仓运维自动化；维护 StarRocks 物化视图刷新。
- 持续跟踪 Iceberg 二级索引/地理空间能力 GA，适时替换过渡性外置索引。

| 阶段 | 状态 | 目标 | 主要风险 | 退出条件 |
|------|------|------|---------|---------|
| 0 | **已完成** | 详单先行迁移 | 多维查询/点查不达标 | 详单多维查询基本达标 ✓ |
| 1 | **当前重点** | 统计迁移（数据量+作业量双大） | 存储过程改写量大、对账复杂、回灌耗时 | 作业改写对账通过 + 数据回灌完成 + 多维/并发达标 |
| 2 | 后续 | 统一下线 | 实时/运维短板 | MPP + 自研格式安全下线 |

### 6.3 关键技术难点与对策

> 按当前阶段（统计迁移）重排优先级：作业量与数据量相关难点最高，详单点查降为"已基本解决/剩余兜底"。

| 难点 | 风险 | 对策 |
|------|------|------|
| **大量 MPP 存储过程改写（当前最大工程量）** | 最高 | 血缘梳理 + 分批分级；SQL 类半自动转写、过程式人工重构；统一调度编排 DAG；逐作业等价对账 |
| **海量统计数据回灌 / 增量双写** | 高 | Spark 批量回灌 + 分区分批 + 文件大小/并发控制；迁移期 MPP↔Iceberg 增量双写 |
| **统计多维并发 SLA** | 中 | StarRocks 物化视图预聚合 + 资源组隔离 + 缓存预热（CACHE SELECT） |
| **加工时效（原 MPP 近实时 vs Spark 批）** | 中 | 关键链路用微批/更短调度周期；必要时 StarRocks 端补充近实时汇聚 |
| **海量小文件/写放大** | 中 | Spark 定期 Compaction + 合理分区粒度 + 批量提交 |
| **详单冷数据随机点查（剩余子风险）** | 中 | 多维查询已达标；冷随机点查用外置 KV/HBase 二级索引兜底 |
| **迁移期一致性** | 中 | 双写双查对账 + 灰度 + 可回退 |

### 6.4 风险登记与回退预案

- **R1 存储过程改写工作量/对账风险（当前首要）**：分批改写 + 自动转写 + 逐作业对账控制风险，未达标作业暂留 MPP，不强迁。
- **R2 数据回灌耗时/资源冲突**：错峰回灌、限流并发、分区分批，必要时临时扩 Spark 资源。
- **R3 加工时效回退**：Spark 批时效不及原 MPP 时，关键链路改微批/缩短周期或 StarRocks 端补充近实时汇聚。
- **R4 详单冷数据点查个案**：少数纯随机高基数冷点查用外置 KV 索引兜底；多维查询已达标，不影响主体。
- **R5 资源/成本超预期**：分离存算（StarRocks Shared-Data）+ 对象存储控成本；按热度分层缓存。

### 6.5 组件级迁移映射

| 现状组件 | 目标组件 | 迁移可行性 | 说明 |
|---------|---------|-----------|------|
| 自研 HDFS 文件格式 | **Iceberg + Parquet/ORC** | 高 | 标准化、跨引擎；需 Spark 做格式转换/回灌 |
| 详单加工 / ETL / 入湖 | **Spark on Iceberg** | 高 | Spark 为湖内计算引擎，负责排序聚簇写入、Compaction |
| HBase 详单索引 | **Iceberg 排序/Bloom + Data Cache（主）+ 外置 KV 兜底；StarRocks 内表仅极热按需** | 中 | 因内表弱化，高基数点查以 Iceberg 侧 + 外置索引为主（见 4.3） |
| 自研查询组件（仅点查） | **StarRocks SQL** | 高 | 统一 SQL 入口，天然支持多维查询 |
| 统计 MPP 集群（存储+计算） | **Iceberg 存储 + Spark 计算 + StarRocks 查询** | 高 | 加工归 Spark、查询归 StarRocks |
| MPP 存储过程 | **Spark 批作业 / Spark SQL（主）+ 可选 StarRocks 物化视图（查询加速）** | 中—高 | 逻辑改写量大，但可声明式化、可维护 |
| 实时点查（无明确实时仓） | **StarRocks 查询为主；真正实时按需用主键表（弱化）或保留轻量实时层** | 中 | 内表弱化下不依赖大规模主键表 |

## 七、结论与建议

1. **方向正确且与 SEQ 同构**：把存算重心搬回湖中——**Iceberg 存、Spark 算、StarRocks 查**，本质是"做一个开放栈版本的 SEQ"，在开放性、多维查询、计算解耦、资源复用上优于现状与 SEQ。
2. **用第一性原理抓重点**：一切性能 = **读得少 × 算得快**；多维聚合靠"算得快"（StarRocks 主场），详单点查靠"读得少"（需数据层工程化补齐）。两条路线**只是侧重不同、可互相借鉴**，不存在"非此即彼"。
3. **详单已先行迁移、多维查询基本达标**：受市场刚需驱动，详单先行迁入 Iceberg + StarRocks，经数据层优化（分桶/Bloom/Saturn 排序）多维查询已基本达标，剩余仅"冷数据纯随机点查"用外置索引兜底。
4. **当前真正的硬仗是统计数据迁移（量大 + 作业多）**：难点不在查询，而在 **① 海量回灌、② 大量 MPP 存储过程向 Spark 改写**；按"作业主线 + 数据主线"双线推进，全程灰度 + 可回退。
5. **客观看待与 SEQ 的差距**：详单点查、时空分析、实时仓成熟度上短期不及 SEQ，需接受"用工程化补齐 + 内表弱化换开放与解耦"的权衡；中长期随引擎演进与 Iceberg 索引 GA，差距收窄，开放栈生态与人才优势持续放大。
